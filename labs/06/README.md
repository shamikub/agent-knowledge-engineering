# Lab 06 · 出發前改航班

## 情境說明

距離出發還有幾天，旅客 B 突然需要延後抵達巴黎——他把週六早上 10:00 的航班改成了下午班。這個改動看似只影響 B 自己，但實際上牽連了好幾個共同預訂：週五晚上兩人一起的餐廳訂位（19:00，兩位）、兩人共住的雙人房（A 仍照常入住）、以及週六上午兩人各持一張的景點門票（09:00）。旅客 A 的行程呢？旅客 B 趕不上晚餐嗎？門票能改場次嗎？這個 Lab 要你建立一個系統，能自動推算這些連鎖影響，並模擬執行改訂動作。

## 你會學到什麼

- 如何把一個異動事件（改航班）的影響，自動傳遞到相關的預訂項目上
- 什麼是「冪等性」（idempotency）：同樣的改訂請求送兩次，結果應該一樣；不同請求用同一個 key 送，應該要偵測衝突
- 如何設計一個需要「先核准再執行」的兩階段動作流程
- 如何用回歸測試確保新功能不會破壞原有行為

## 開始前確認

- 已讀完 [第 6 章講義](../../lectures/chapter6/intro.md)（持續學習與執行控制）
- 完成 Lab 03，理解連鎖事件與影響查詢的概念
- 了解什麼是「狀態機」（state machine）以及幂等操作的基本概念

## 執行方式

從倉庫根目錄執行下列指令，觀察基線輸出：

```bash
python3 course.py 06
```

執行後你會看到旅客 B 改航班後，系統對各個共同預訂的影響判斷，以及模擬執行餐廳改訂的流程。接著根據 [SPEC](SPEC.md) 測試不同情境並實作冪等性驗證，再核對 [EXPECTED](EXPECTED.md)。

## 可能卡住的地方

- **旅客 A 的入住為什麼不受影響？** 雙人房是兩人共訂的，B 改航班後，A 能不能照常辦理入住？旅館的預訂是以「房間」為單位還是以「每位旅客」為單位？
- **「先核准再執行」是什麼意思？** 試著想像：如果改訂動作是不可逆的（例如已刷卡），你會希望系統先給你一個「預覽」，你確認後才真正執行。這個兩階段流程在程式裡要怎麼表示？
- **同一個 key 送不同參數為什麼要回報衝突？** 如果第一次送「2 位」，第二次送「1 位」，兩者用同一個 key，系統無法知道哪個才是你真正的意圖，所以必須報錯而不是靜悄悄地覆蓋。

## 驗收標準

核對 [EXPECTED.md](EXPECTED.md)，重點確認：

1. 餐廳訂位需確認改為一位或改期（B 趕不上）
2. 旅客 A 照常入住，雙人房保留
3. A 的門票照用，B 的門票需確認能否改場
4. 模擬動作示範把餐廳改為一位，且先要求核准再執行
5. 同參數重送回報「已處理」，同 key 但不同人數回報「衝突」

驗收指令：

```bash
python3 course.py 06
python3 -m unittest discover -s tests -v
```
