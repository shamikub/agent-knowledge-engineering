# 1.1 文件解析的每一層

[← 上一頁](intro.md) · [本章導覽](intro.md) · [總目錄](../../README.md#課程地圖) · [下一頁 →](02-speech.md)

## 學習目標

完成本節後，你應能：

1. 說出文字型 PDF（text-layer PDF）與掃描 PDF 的本質差異，以及各自的抽取流程。
2. 手算**字元錯誤率（Character Error Rate，CER）**，並解釋為何 CER=0 仍可能抽錯表格資料。
3. 列舉跨欄（merged cell）標頭的三種常見失敗模式，說明何種指標才能偵測到這些失敗。
4. 比較模板比對、LayoutLMv3 和 Table Transformer 三種方法對同一個跨欄標頭任務的假設與故障模式。

---

## 任務定義

### 輸入

| 來源 | 格式 | 典型挑戰 |
|------|------|----------|
| 訂位確認信 | 文字型 PDF | 雙欄排版、字元座標交錯 |
| 旅館住宿清單 | 掃描 PDF / TIFF | 低解析、斜角、手寫批注 |
| 火車時刻表 | PDF 內嵌表格 | 跨欄標頭、跨列合併儲存格 |

### 輸出

結構化文字與表格，每一筆記錄應包含：

```
{
  "page": 整數,
  "bbox": [x0, y0, x1, y1],   # 以點或像素為單位
  "text": "字串",
  "confidence": 0.0–1.0,
  "table_cell": {              # 若在表格中
    "row": 整數, "col": 整數,
    "row_span": 整數, "col_span": 整數
  }
}
```

### 子任務清單

1. 文字區域偵測（text region detection）
2. 裁切與方向校正（deskew / orientation correction）
3. 字串辨識（OCR）
4. 閱讀順序重建（reading order reconstruction）
5. 表格偵測（table detection）
6. 表格結構辨識（table structure recognition）
7. 儲存格對齊與跨度還原（cell alignment & span recovery）

---

## 從元件到架構

每個步驟的輸入與輸出如下，資料依序向下流動：

```
原始 PDF / 影像
   │
   ▼ [步驟 1] 文字區域偵測
   │  輸入：整頁影像
   │  輸出：文字塊邊界框清單
   │
   ▼ [步驟 2] 裁切與方向校正
   │  輸入：文字塊邊界框
   │  輸出：方向角度、旋轉後影像
   │
   ▼ [步驟 3] OCR（字串辨識）
   │  輸入：文字塊影像片段
   │  輸出：字元序列 + 信心分數
   │
   ▼ [步驟 4] 閱讀順序重建
   │  輸入：多個文字塊（含 bbox）
   │  輸出：線性排列的段落序列
   │
   ▼ [步驟 5–7] 表格偵測 → 結構辨識 → 儲存格對齊
      輸入：整頁影像 + 文字塊座標
      輸出：帶 row/col/span 的結構化表格
```

**文字型 PDF 的捷徑**：pdfminer / pdfplumber 可直接讀文字層（字元座標已內嵌），跳過步驟 2–3，但仍需步驟 4–7 重建順序與結構。

## 完整算例：CER=0 卻配錯欄位的反例

### 情境

你拿到一張旅館住宿比較表格，原始正確版本如下：

```
┌──────────────┬──────────────────────────┐
│   住宿名稱    │        設備              │
│              ├─────────────┬────────────┤
│              │  洗衣機     │  烘衣機    │
├──────────────┼─────────────┼────────────┤
│ 民宿 A        │     ✓       │     ✗      │
│ 民宿 B        │     ✗       │     ✓      │
└──────────────┴─────────────┴────────────┘
```

### 工具甲的輸出

工具甲 OCR 漏認「烘」字：

- 辨識結果：`洗衣機 衣機`
- 參考文字（忽略空白後）：`洗衣機烘衣機`（6 字元）
- 編輯距離：刪去「烘」→ 1 步

```
CER = 編輯距離 / 參考字元數 = 1 / 6 ≈ 0.167（約 16.7%）
```

### 工具乙的輸出

工具乙 OCR 完全正確，六字全對，CER = 0。
但表格結構辨識把「烘衣機」那一欄的值，整欄位移一格，變成：

```
民宿 A：洗衣機=✓，烘衣機=✓   ← 錯（實為 ✗）
民宿 B：洗衣機=✗，烘衣機=✗   ← 錯（實為 ✓）
```

### 為何 CER 偵測不到這個錯誤？

CER 只衡量「辨識出的字元序列與參考序列的差距」，不管字元放在哪個儲存格。工具乙的字認對了，但行列對應關係錯了。

**解法：加入結構指標。**

- **GriTS（Grid Table Similarity）**：分別計算拓撲正確率（儲存格連接關係）、內容正確率（儲存格文字）、位置正確率（bbox 重疊 IoU），三分指標都要達標才算正確。
- **欄位正確率（Column Accuracy）**：每個儲存格的 (row, col) 是否與標注吻合。

## 方法比較：以「跨欄標頭表格」為基準任務

下表以「住宿名稱 + 設備（洗衣機、烘衣機跨欄）」這道題為共同基準：

| 方法 | 核心假設 | 成本 | 跨欄標頭處理 | 故障模式 |
|------|----------|------|--------------|----------|
| **模板比對**（template matching） | 表格版面固定、欄位座標已知 | 極低（規則撰寫一次） | 需手動標注每個跨欄座標 | 版面改版後欄位座標移位，全面失效 |
| **LayoutLMv3** | 文字、位置、影像 patch 三流合一的預訓練 Transformer | 中（GPU 推論，微調需數百筆標注） | 可從位置 embedding 推斷跨欄關係 | 表格密度高時 token 超長；未微調資料集上泛化有限 |
| **Table Transformer**（TATR） | 把列、欄、標頭當物件偵測問題（DETR 架構） | 中（GPU 推論，PubTables-1M 預訓練） | 以獨立類別（column header）偵測跨欄行 | 低解析掃描導致框偏移；文字極稀少時誤判邊界 |

**選型建議**

- 文件版面固定（如火車票格式統一）→ 先試模板比對，成本最低。
- 多樣化文件、有 GPU → Table Transformer 配合 Docling 是目前最省標注成本的起點。
- 需要語意欄位分類（如「價格欄」vs「設施欄」）→ LayoutLMv3 微調。

## 研究與實務

### PubTables-1M Benchmark

- **論文**：Smock et al., 2022，[arXiv:2110.00061](https://arxiv.org/abs/2110.00061)
- **資料集**：~100 萬張科學論文表格，含結構標注
- **評估指標**：GriTS（Grid Table Similarity）分三個子分數：
  - `GriTS_Top`：拓撲正確率（儲存格連接）
  - `GriTS_Con`：內容正確率（文字吻合）
  - `GriTS_Loc`：位置正確率（bbox IoU）
- **Table Transformer 基準結果**（2022，PubTables-1M 測試集）：`GriTS_Top ≈ 0.979`

### GriTS 指標說明

給定預測表格 $\hat{T}$ 與標注表格 $T^*$，GriTS 以最大二部匹配（maximum bipartite matching）對齊儲存格後計算：

```
GriTS = (matched_score) / max(|T*|, |T_hat|)
```

其中 `matched_score` 依子指標不同，分別為拓撲相似度、文字相似度或 bbox IoU 的加總。

## 工具與實驗

### Docling：一行指令完成文件轉換

[Docling](https://github.com/DS4SD/docling)（IBM Research，2024）整合了版面分析、OCR、表格結構辨識，底層使用 Table Transformer。

```python
from docling.document_converter import DocumentConverter

converter = DocumentConverter()
result = converter.convert("住宿清單.pdf")

# 取得所有表格（以 Markdown 格式輸出）
for table in result.document.tables:
    print(table.export_to_markdown())

# 取得帶 bbox 的文字塊
for element, _level in result.document.iterate_items():
    print(element.text, element.prov)   # prov 包含 page, bbox
```

**Docling 實作了哪一層**：步驟 1（版面偵測）、步驟 3（OCR，使用 EasyOCR 或 Tesseract）、步驟 5–7（Table Transformer 表格結構）。步驟 4（閱讀順序）由版面分析模型輸出的區塊排序決定。

## 習題

**習題 1（機制）**：一份旅館比較 PDF 的文字層內，「洗衣機」三個字的 x 座標分別是 102、118、134 pt，另一欄「烘衣機」的 x 座標是 210、226、242 pt。請說明：若以「x 座標由小到大」單純排序，抽取出的字串順序為何？為何閱讀順序重建模組必須先辨識欄界？

<details>
<summary>解答</summary>

「洗衣機烘衣機」六個字的 x 座標順序是 102、118、134、210、226、242，恰好本來就是由小到大，所以這個例子「湊巧」正確。

真正的問題發生在**多欄頁面**：左欄的第二段（x ≈ 50–200）與右欄的第一段（x ≈ 220–370）若混排，左欄第二段的 x 值可能大於右欄第一段的某些字，導致交錯。正確作法是先用版面分析辨識欄界，把兩欄分開後，各自由上到下、左到右排序，再合併為「先讀完左欄、再讀右欄」的線性順序。

</details>

---

**習題 2（手算 CER）**：OCR 工具對「米蘭中央車站」（5 字）的辨識結果是「米蘭中夹車站」（5 字，「央」誤認為「夹」）。

1. 計算 CER。
2. 若同一工具對「羅馬特米尼車站」（7 字）辨識為「羅馬特尼車站」（6 字，漏了「米」），CER 為何？
3. 兩者 CER 較高的那個，是否代表「絕對錯誤字數」較多？請說明。

<details>
<summary>解答</summary>

**第 1 小題**

參考文字：`米蘭中央車站`（5 字，不含空格）
辨識文字：`米蘭中夹車站`（5 字）
差異：第 4 字「央」→「夹」，1 次替換（substitution）。

```
CER = 1 / 5 = 0.20（20%）
```

**第 2 小題**

參考文字：`羅馬特米尼車站`（7 字）
辨識文字：`羅馬特尼車站`（6 字）
差異：漏了「米」，1 次刪除（deletion）。

```
CER = 1 / 7 ≈ 0.143（約 14.3%）
```

**第 3 小題**

兩者都只有 **1 個絕對錯誤字元**，但「米蘭中央車站」的 CER（20%）高於「羅馬特米尼車站」（14.3%），因為分母（參考字元數）較小。CER 是**相對比率**，不直接代表絕對錯誤數量。評估大量文件時，應同時報告絕對編輯距離與 CER，才能完整呈現錯誤規模。

</details>

---

**習題 3（選型）**：你的公司需要每月處理約 500 份旅館報價單 PDF。報價單由 20 家旅館提供，格式各異（有些是文字型 PDF，有些是掃描）；表格多有跨欄標頭，欄位名稱每季可能微調。開發資源：一名工程師、一台配備消費級 GPU（RTX 3060）的工作站。請說明你會選擇哪種方法，理由為何，以及你最擔心的一個故障模式。

<details>
<summary>解答</summary>

**建議方案**：先用 **Docling（內建 Table Transformer）** 作為基線。

**理由**：
- 20 家旅館格式各異，模板比對需維護 20 套模板，格式微調時維護成本爆增。
- RTX 3060（8–12 GB VRAM）足以執行 Table Transformer 推論（模型約 110M 參數）。
- Docling 開箱即用，不需自行標注訓練資料。

**最擔心的故障模式**：
跨欄標頭的**欄位位移**——Table Transformer 以物件偵測框出欄位邊界，掃描解析度不足或表格線印刷模糊時，欄位邊界框可能偏移半格，導致儲存格對應錯列（CER=0 但 GriTS_Top 下降）。建議：抽樣人工核驗 GriTS_Con，並對掃描品質差的頁面加一道影像前處理（對比度增強、去噪）。

</details>
