# 4.5 從檢索到回答

## 學習目標

讀完本節後，你應該能：

- 列出 RAG 管線的四個模組（Retriever、Reranker、Prompt Builder、LLM），並說明各自的輸入輸出介面
- 描述每個模組的典型失敗模式
- 解釋 Lost in the Middle 效應，並說明它如何影響 prompt 的文件排列順序
- 說明多跳查詢（multi-hop query）的流程，以及何時需要它
- 設計一個帶引用驗證的 RAG 評估方案（使用 ALCE 方法）

**先備知識：** 4.2–4.4 節的檢索方法；基本的 LLM prompt 概念。

---

## 任務定義：檢索器 + 生成器

RAG（Retrieval-Augmented Generation）的核心思路：LLM 的參數記憶有截止日期，且無法追蹤動態更新的文件（如最新取消政策）。把**外部知識庫的檢索**和**LLM 的生成能力**結合，讓 LLM 根據即時取回的證據回答，而非依靠訓練時記住的知識。

**各模組的輸入輸出介面：**

```
使用者查詢 q（字串）
   │
   ▼
┌─────────────┐  輸入：q
│  Retriever  │  輸出：候選文件列表（doc, score）× top-k
└─────────────┘
   │
   ▼
┌──────────────┐  輸入：候選文件列表 × top-k
│   Reranker   │  輸出：重排後文件列表 × top-m（m ≤ k）
└──────────────┘  （若無 reranker，直接傳遞）
   │
   ▼
┌───────────────────┐  輸入：重排後文件、使用者查詢 q
│   Prompt Builder  │  輸出：格式化的 prompt（含證據段落）
└───────────────────┘
   │
   ▼
┌─────┐  輸入：prompt
│ LLM │  輸出：回答 + 引用標記
└─────┘
   │
   ▼
最終回答（含引用）
```

---

## 四個模組的失敗模式

| 模組 | 失敗模式 | 診斷方法 |
|------|----------|----------|
| Retriever | 正確答案不在 top-k（recall 低）| Oracle retrieval：手動把答案加入候選，看 LLM 能否正確回答 |
| Reranker | 答案在候選集但排名靠後（precision 低）| 比較重排前後的排名，查看答案的 rank 變化 |
| Prompt Builder | 文件截斷、順序不佳（Lost in the Middle）| 交換文件順序，觀察答案是否改變 |
| LLM | 忽略證據、幻想、引用錯誤 | ALCE 引用評估；比較有無正確證據的回答 |

## 完整算例：「夜車幾點抵達薩爾斯堡」的端對端流程

### 資料集

```
D1（班次表，最新版）：「夜車 EN 466，23:40 從維也納中央車站出發，次日 06:15 抵達薩爾斯堡。」
D2（住宿說明）：「旅館入住時間 15:00 後，退房 11:00 前。」
D3（舊版班次表，已過期）：「夜車 EN 466，22:10 出發，05:30 抵達。」
D4（行程說明）：「夜間列車是跨日旅行的首選，請攜帶睡眠面罩。」
```

### 步驟一：Retriever

```
輸入：q = "夜車幾點抵達薩爾斯堡"
使用 BM25 + bi-encoder RRF，top-k=3

BM25 命中：D1（有「夜車」、「薩爾斯堡」）、D3（同）
Bi-encoder 命中：D1、D4（「夜間列車」語意近似）、D3
RRF 融合後 top-3：[D1, D3, D4]

輸出：候選列表 [(D1, 0.062), (D3, 0.058), (D4, 0.041)]
```

### 步驟二：Reranker

```
輸入：[(D1, 0.062), (D3, 0.058), (D4, 0.041)]
Cross-encoder 對每對 (q, Dᵢ) 算相關性分數：
  (q, D1) → 0.95（高度相關：直接回答時刻）
  (q, D3) → 0.88（相關，但是舊版本）
  (q, D4) → 0.42（部分相關：提到夜車但無時刻）

重排後 top-3：[D1(0.95), D3(0.88), D4(0.42)]
輸出：[D1, D3, D4]（順序改變但結果相同；D1 仍第一）
```

### 步驟三：Prompt Builder

```
輸入：查詢 q、文件 [D1, D3, D4]（取 top-2 以控制 token 長度）
輸出（格式化 prompt）：

---
你是旅遊行程助手。請根據以下證據回答問題，並標明引用來源。

[文件 1] 夜車 EN 466，23:40 從維也納中央車站出發，次日 06:15 抵達薩爾斯堡。
[文件 2] 夜車 EN 466，22:10 出發，05:30 抵達。

問題：夜車幾點抵達薩爾斯堡？
---
```

### 步驟四：LLM 生成

```
輸入：上述 prompt
輸出：「夜車 EN 466 於次日 06:15 抵達薩爾斯堡 [文件 1]。」
```

**此例正確：** LLM 採用了文件 1 的時刻（最新版本），並正確忽略了文件 2 的舊資料。

---

### 反例：正確引用但答案錯誤

假設 Prompt Builder 把文件順序倒置（D3 排第一、D1 排第二）：

```
[文件 1] 夜車 EN 466，22:10 出發，05:30 抵達。       ← 舊版
[文件 2] 夜車 EN 466，23:40 從維也納出發，06:15 抵達。 ← 新版
```

LLM 輸出：「夜車 EN 466 於次日 05:30 抵達薩爾斯堡 [文件 1]。」

**引用正確**（確實引用了文件 1），但**答案錯誤**（使用了過期時刻）。

這個反例說明：
1. 引用標記不代表答案正確，需要獨立驗證
2. Prompt Builder 的文件順序（以及選哪份文件放入 prompt）至關重要
3. 版本過濾應在 Retriever 層就排除過期文件（例如 metadata 過濾 `date >= 2024-01`）

## 多跳查詢（Multi-hop Query）

有些問題需要跨多份文件推理：

**查詢：「夜車抵達薩爾斯堡後，旅館最早幾點能入住？」**

這個問題至少需要兩份文件：
1. 夜車的抵達時刻（D1）
2. 旅館的入住時間（D2）

單次查詢可能找到其中一份，但不保證兩份都在 top-k。多跳 RAG 的流程：

```
跳 1：
  q₁ = "夜車幾點抵達薩爾斯堡"
  → 找到 D1（06:15 抵達）
  → 中間答案：抵達時刻 = 06:15

跳 2：
  q₂ = "薩爾斯堡旅館最早入住時間"（由系統根據中間答案生成）
  → 找到 D2（入住 15:00 後）
  → 中間答案：入住時間 = 15:00

最終推理：
  06:15 抵達，15:00 才能入住 → 需要等待約 9 小時
```

**實作要點：**
- 第一跳的中間答案要能被系統解析（結構化輸出更好）
- 第二跳的查詢可以由 LLM 根據第一跳答案自動生成（Chain-of-Thought）
- 每跳的 qrels 標註要分開，才能診斷是哪一跳出錯

## Lost in the Middle 效應

研究發現（Liu et al., 2023），LLM 在處理長 prompt 時，最能利用的是**排在開頭和結尾**的文件，中間位置的文件容易被忽略。這稱為 Lost in the Middle 效應。

**實際影響：**
- 若最相關的文件被 Prompt Builder 排在 prompt 中間（位置 4-8），LLM 的回答準確率可能下降 20% 以上
- 在 top-10 候選中，把相關性最高的文件放在位置 1（開頭）或位置 10（結尾）比放在位置 5 效果更好

**實務建議：**
- 在 Prompt Builder 把 Reranker 給出的最高分文件放在第一位（或最後一位）
- 控制放入 prompt 的文件數，避免過長 prompt 稀釋重要信號
- 可用「先刪後問」：LLM 先對每份文件做二元相關性判斷，再把相關文件重新組合成最終 prompt

## ALCE 引用評估方法

ALCE（Attributed Language modeling with Citation Evaluation）提供了一套評估 RAG 系統引用品質的方法，分三個維度：

| 指標 | 意義 | 計算方式 |
|------|------|----------|
| **Citation Recall** | 答案中的所有聲明是否都有引用支持 | 有引用支持的聲明數 / 總聲明數 |
| **Citation Precision** | 引用的文件是否真的支持對應的聲明 | 實際支持的引用數 / 總引用數 |
| **Answer Correctness** | 最終答案是否正確 | 與 gold answer 比較（EM 或 F1） |

**評估流程：**

1. 對每筆查詢，收集 LLM 的回答和引用
2. 人工或用 NLI 模型判斷「引用的文件是否蘊含（entail）被引用的聲明」
3. 分別統計三個指標

**反例說明：**
- Citation Precision = 1.0 但 Answer Correctness = 0：引用的是過期文件，引用本身在文件中找得到，但文件內容是錯的
- Citation Recall = 0 但 Answer Correctness = 1：LLM 憑記憶回答正確，但沒有引用文件（幻想風險高）

---

## 方法比較：三種 RAG 架構

| 架構 | 描述 | 優點 | 缺點 |
|------|------|------|------|
| Naive RAG | 單次查詢 → 拼接 top-k → LLM | 簡單、低延遲 | 無法處理多跳；Lost in the Middle 影響大 |
| RAG + Reranker | 加一層 cross-encoder 精排 | 排序更精確，前幾名更相關 | 多一次推論成本；召回問題仍在上游 |
| Multi-hop RAG | 多輪查詢，每輪根據中間答案生成下一個查詢 | 能處理跨文件推理 | 延遲高；錯誤傳播（第一跳錯，後續都錯） |

## 習題

**題 1（機制）：** 一個 RAG 系統回答「住宿含早餐嗎？」時引用了正確的訂位確認信，但回答是「不含早餐」（實際上含）。請描述可能的失敗原因，以及如何用 oracle retrieval 和引用評估定位問題。

<details>
<summary>解答</summary>

**可能原因：**

1. **LLM 忽略了引用文件中的正確資訊**（Prompt Builder 把文件排在中間，Lost in the Middle）
2. **LLM 錯誤理解了文件內容**（例如把「含早餐（需額外付費）」誤讀為「不含」）
3. **Prompt Builder 截斷了文件**，含早餐的那一句話被切掉了

**定位步驟：**

1. **Oracle retrieval 測試：** 手動把含正確早餐資訊的段落直接插入 prompt 第一位，觀察 LLM 是否能正確回答 → 若可以，問題在 Prompt Builder 的文件位置或截斷
2. **引用評估（ALCE）：** 檢查 Citation Precision，確認 LLM 聲稱「不含早餐」時引用的文件段落是否真的支持這個聲明 → 若引用的段落寫的是「含早餐」但 LLM 仍說「不含」，問題在 LLM 的理解
3. **Ablation：** 把文件移到 prompt 的第一位重跑，若答案變正確，確認是 Lost in the Middle 問題

</details>

**題 2（手算）：** 一個 RAG 系統回答一筆查詢，回答包含三個聲明：(a) 夜車 06:15 到達 [文件 1]，(b) 旅館最早 15:00 入住 [文件 2]，(c) 因此需等待約 9 小時 [文件 1, 文件 2]。已知文件 1 確實支持聲明 a，文件 2 確實支持聲明 b，但聲明 c 是推理結論、沒有任何文件直接寫出。計算 Citation Recall、Citation Precision 和 Answer Correctness（假設計算正確）。

<details>
<summary>解答</summary>

**定義：**
- 聲明 a：有引用 [文件 1]，文件 1 支持 → Citation 有效
- 聲明 b：有引用 [文件 2]，文件 2 支持 → Citation 有效
- 聲明 c：有引用 [文件 1, 文件 2]，但兩份文件都不直接寫「需等待 9 小時」→ 文件不蘊含此聲明（需要推理），視為 Citation Precision 失敗

**計算：**
- Citation Recall = 有支持的聲明數 / 總聲明數 = 2/3 ≈ 0.667
  （聲明 a 和 b 有支持；聲明 c 沒有文件直接支持）
- Citation Precision = 實際支持的引用數 / 總引用數
  引用總計：聲明 a 的 [文件 1]（1 個）+ 聲明 b 的 [文件 2]（1 個）+ 聲明 c 的 [文件 1, 文件 2]（2 個）= 4 個引用
  有效引用：聲明 a 的 [文件 1]（1）+ 聲明 b 的 [文件 2]（1）= 2 個
  Citation Precision = 2/4 = 0.500
- Answer Correctness = 1（06:15 到，15:00 才能入住，等待 8h45m ≈ 9h，算正確）

**結論：** 推理聲明降低了 Citation Precision，但不影響 Answer Correctness。實務上可允許推理聲明不引用，或額外標記為「推理」類別。

</details>

---

**題 3（選型）：** 你的 RAG 系統在單跳查詢的 F1 已達 0.80，但在需要跨兩份文件推理的查詢上 F1 只有 0.35。你應該先加多跳 RAG 還是先加 reranker？說明理由。

<details>
<summary>解答</summary>

**先加多跳 RAG。**

單跳查詢 F1 = 0.80 表示單次檢索的品質已經不錯，reranker 能帶來的提升空間有限（估計最多到 0.85）。

跨文件推理的低 F1 是因為單次查詢無法同時找到兩份互補的文件，reranker 只能重排已有候選，無法解決「答案需要兩份文件才能推導」的結構性問題。

**多跳 RAG 的加法：**
1. 在第一跳找到中間答案（例如夜車抵達時刻）
2. 根據中間答案生成第二跳查詢（例如「薩爾斯堡旅館入住時間」）
3. 合併兩跳的證據再生成最終答案

注意：多跳 RAG 會增加延遲（兩次 LLM 呼叫），需要評估是否符合系統的延遲預算。若延遲不可接受，可改用「在一個 prompt 內讓 LLM 自行分解多跳查詢」（ReAct / Chain-of-Thought）。

</details>
