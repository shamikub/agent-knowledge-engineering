## Part 1：倒排索引

### 為什麼不直接掃描每份文件？

想像你在旅行前整理了三百封 email，要找「有提到洗衣機」的信。最直接的做法是從第一封讀到最後一封。這叫做**線性掃描（linear scan）**，查詢時間與文件數成正比。

書本的末頁索引解決了同樣的問題：它把「每個詞出現在哪一頁」預先整理好，查詢時直接翻到那一頁，不需要重讀全書。

電腦的**倒排索引（inverted index）**就是這個想法的實作：

- **正向索引（forward index）**：文件 → 它包含哪些詞（書本內容）
- **倒排索引（inverted index）**：詞 → 哪些文件包含它（書末索引）

建索引在事前做一次，查詢時只需走兩個詞的 posting list 再合併，速度與**匹配文件數**成正比，而非與**全部文件數**成正比。這是搜尋引擎能在毫秒內回答的原因。

---

### 任務定義

| 項目 | 說明 |
|------|------|
| 輸入 | 文件集合 D = {d₁, d₂, …, dₙ}，每份已切詞成 token 序列 |
| 輸出 | 映射 term → posting list；每筆 posting 為 (doc_id, freq, positions) |
| 子任務 | 分詞、正規化、建索引、查詢執行 |
| 常見基線 | Elasticsearch / Lucene 的預設分析器 |

**符號說明：**

- `t`：詞（term）
- `d`：文件（document）
- `freq(t, d)`：詞 t 在文件 d 中出現的次數
- `positions(t, d)`：詞 t 在文件 d 中出現的位置列表（以 token 序號計）

---

### 架構：從原始文字到 posting list

整個建索引流程分為四步。每步的輸出就是下一步的輸入。

```
原始文字
   ↓
1. 分詞（Tokenization）
   ↓
2. 正規化（Normalization）
   ├── 轉小寫（lowercase）
   ├── 詞幹化（stemming）或詞形還原（lemmatization）
   └── 移除停用詞（stopwords removal）
   ↓
3. 建 Posting List
   ↓
4. 布林查詢執行（AND = merge / OR = union）
```

#### 步驟一：分詞

中文沒有空格，需要先用切詞工具（如 jieba、ckip-transformers）切出詞的邊界。英文以空格和標點為界較容易，但「check-in」要算一個詞還是兩個詞，取決於應用需求。

**切詞粒度的影響：**「洗烘衣機」如果切成「洗烘」＋「衣機」，查詢「洗衣機」就永遠找不到這份文件。

#### 步驟二：正規化

**轉小寫：** 讓「Hotel」和「hotel」視為同一個詞。代價：專有名詞「APPLE」（公司）和「apple」（水果）被合併。

**詞幹化（stemming）：** 把「running」、「runs」、「ran」都化為詞根「run」。英文常用 Porter Stemmer；中文通常不需要，因為詞形變化少。代價：過度化簡可能把不同意思的詞合併（over-stemming）。

**停用詞（stopwords）：** 移除「的」「是」「在」「and」「the」等高頻但幾乎無辨識力的詞，以縮小索引大小、加快查詢。代價：「不 可 取消」裡的「不」如果被移除，布林查詢就無法區分「可取消」與「不可取消」。**在法律與條款類文件要特別小心。**

#### 步驟三：建 Posting List

對每個正規化後的 token，將 (doc_id, position) 記錄到該詞的 posting list。最後統計每份文件的出現次數 freq。

#### 步驟四：布林查詢執行

- **AND（交集 / merge）：** 走兩個 posting list，以雙指針找共同的 doc_id。只回傳同時出現兩個詞的文件。
- **OR（聯集 / union）：** 走兩個 posting list，合併所有 doc_id。
- **NOT：** 在 AND 後排除某個詞的文件，需要整份文件集合當背景。

---

### 完整算例：手建倒排索引

#### 原始文件

```
D1（訂位確認信）：「您的訂位已確認，住宿含早餐，不含洗衣機服務。」
D2（取消政策）：「取消訂位需在入住前 48 小時辦理，逾期不予退款。」
D3（住宿說明）：「本房型提供洗衣機與烘衣機，洗烘費用另計。」
```

#### 步驟一：切詞後（簡化示意，移除標點）

```
D1：您 的 訂位 已 確認 住宿 含 早餐 不含 洗衣機 服務
D2：取消 訂位 需 在 入住 前 48 小時 辦理 逾期 不予 退款
D3：本 房型 提供 洗衣機 與 烘衣機 洗烘 費用 另計
```

#### 步驟二：正規化（移除停用詞「的」「已」「在」「與」「本」）

```
D1（pos 從 0 起）：訂位(0) 確認(1) 住宿(2) 含(3) 早餐(4) 不含(5) 洗衣機(6) 服務(7)
D2：取消(0) 訂位(1) 需(2) 入住(3) 前(4) 48(5) 小時(6) 辦理(7) 逾期(8) 不予(9) 退款(10)
D3：房型(0) 提供(1) 洗衣機(2) 烘衣機(3) 洗烘(4) 費用(5) 另計(6)
```

#### 步驟三：倒排索引（term → posting list）

| Term   | Posting list（doc_id, freq, positions）           |
|--------|---------------------------------------------------|
| 訂位   | (D1, 1, [0])、(D2, 1, [1])                        |
| 確認   | (D1, 1, [1])                                      |
| 住宿   | (D1, 1, [2])                                      |
| 不含   | (D1, 1, [5])                                      |
| 洗衣機 | (D1, 1, [6])、(D3, 1, [2])                        |
| 取消   | (D2, 1, [0])                                      |
| 入住   | (D2, 1, [3])                                      |
| 退款   | (D2, 1, [10])                                     |
| 烘衣機 | (D3, 1, [3])                                      |
| 洗烘   | (D3, 1, [4])                                      |

#### 步驟四：執行布林查詢

**查詢 A：「洗衣機 AND 烘衣機」**

```
洗衣機 → [D1, D3]
烘衣機 → [D3]

雙指針 merge：
  D1 vs D3：D1 < D3，左指針前進
  D3 vs D3：相同 → 加入結果
結果：[D3]
```

回傳 D3（住宿說明）。正確：只有 D3 同時提到這兩個詞。

**查詢 B：「洗衣機 OR 烘衣機」**

```
洗衣機 → [D1, D3]
烘衣機 → [D3]

union：[D1, D3]
```

回傳 D1 和 D3。

---

### 反例：「烘衣」和「烘衣機」是不同的 term

現在加入一份新文件：

```
D4（設備補充說明）：「本館提供洗烘設備，烘衣功能需預約。」
切詞後：洗烘(0) 設備(1) 烘衣(2) 功能(3) 需(4) 預約(5)
```

此時：
- `烘衣機` 的 posting list：(D3, 1, [3])
- `烘衣` 的 posting list：(D3, 1, [4])、(D4, 1, [2])

執行「洗衣機 AND 烘衣機」：**D4 不在結果中**，因為 D4 裡的詞是「烘衣」而非「烘衣機」。

這就是**術語不匹配（vocabulary mismatch）**問題：語意相近但字面不同的詞，倒排索引無法自動橋接。解法包括：
- 加入同義詞表（synonym expansion）：在索引時或查詢時把「烘衣」擴展為「烘衣機」
- 改用向量檢索（見 4.3 節）捕捉語意相似度

## Part 2：BM25 排名

### 任務定義：排名而非布林

布林查詢只回答「符合 / 不符合」，所有符合的文件地位相同。現實中使用者需要的是**排名（ranking）**：有十份文件都提到「取消政策」，哪一份最有可能回答你的問題？

BM25（Best Match 25）是**排名檢索（ranked retrieval）**的標準基線，輸入一個自然語言查詢，對每份文件算出一個分數，再取 top-k。

| 項目 | 說明 |
|------|------|
| 輸入 | 查詢 q（切詞後的 token 序列）、文件集合 D |
| 輸出 | 每份文件的分數，用以排序取 top-k |
| 核心思路 | 稀有詞貢獻高（IDF）、詞頻有飽和上限（k1）、長文件做長度懲罰（b） |

---

### 公式與每個符號的意義

對查詢 q 和文件 d，BM25 分數為：

```text
score(q, d) = Σ_{t ∈ q}  IDF(t) × TF_norm(t, d)

其中：

IDF(t) = log( 1 + (N - DF(t) + 0.5) / (DF(t) + 0.5) )

TF_norm(t, d) = TF(t, d) × (k1 + 1) / ( TF(t, d) + K )

K = k1 × ( 1 - b + b × |d| / avgdl )
```

**符號對照表：**

| 符號 | 名稱 | 說明 |
|------|------|------|
| N | 文件總數 | 語料庫大小 |
| DF(t) | 文件頻率（Document Frequency） | 含詞 t 的文件數 |
| TF(t, d) | 詞頻（Term Frequency） | 詞 t 在文件 d 出現幾次 |
| \|d\| | 文件長度 | 文件 d 的 token 數 |
| avgdl | 平均文件長度 | 整個語料庫的 token 數平均值 |
| k1 | 詞頻飽和參數 | 預設 1.2，控制 TF 的飽和速度 |
| b | 長度正規化參數 | 預設 0.75，0 = 不看長度，1 = 完全正規化 |

---

### k1 和 b 的直觀解釋

#### k1：詞頻飽和

TF_norm 的分子是 `TF × (k1 + 1)`，分母是 `TF + K`。當 TF 趨向無窮大時，整個分數趨近 `k1 + 1`。k1 決定「詞出現多次比一次多多少分」。

```text
k1 = 1.2，K = 1（固定，忽略長度效果）：
TF=1  → 1  × 2.2 / (1  + 1) = 1.10
TF=2  → 2  × 2.2 / (2  + 1) = 1.47
TF=5  → 5  × 2.2 / (5  + 1) = 1.83
TF=10 → 10 × 2.2 / (10 + 1) = 2.00  ← 趨近飽和上限 k1+1 = 2.2
TF=∞  → 2.2
```

**k1 越大**：飽和越慢，高頻詞的文件優勢越大。
**k1 越小**：趨近二元（出現或不出現），接近 BM11。

#### b：長度正規化

K = k1 × (1 - b + b × |d| / avgdl)

- **b = 0**：K = k1，完全不看文件長度。長文件和短文件的詞頻效果相同。
- **b = 1**：K = k1 × |d| / avgdl，完全按比例縮放。短文件的詞頻等效地更高。
- **b = 0.75**（預設）：折中。長文件仍有輕微的詞頻懲罰。

**數字說明：** 若 avgdl = 100、k1 = 1.2、b = 0.75：
- 短文件（|d|=50）：K = 1.2 × (0.25 + 0.75 × 0.5) = 1.2 × 0.625 = 0.75
- 長文件（|d|=200）：K = 1.2 × (0.25 + 0.75 × 2) = 1.2 × 1.75 = 2.10

同樣是「TF=2」，短文件的 TF_norm = 2 × 2.2 / (2 + 0.75) = **1.60**，長文件的 TF_norm = 2 × 2.2 / (2 + 2.10) = **1.07**。長文件被合理地懲罰了。

### 完整算例：三份文件、兩個查詢詞

#### 資料設定

```text
N = 3 份文件

D1（訂位確認信，5 tokens）：「確認 訂位 含 洗衣機 服務」
D2（住宿說明，8 tokens）：「房型 提供 洗衣機 烘衣機 洗衣機 費用 另計 預約」
D3（取消政策，6 tokens）：「取消 訂位 48 小時 前 辦理」

avgdl = (5 + 8 + 6) / 3 = 6.33
k1 = 1.2，b = 0.75
```

**查詢：「洗衣機 訂位」**（查詢詞 t1 = 洗衣機、t2 = 訂位）

#### 步驟一：計算 IDF

```text
「洗衣機」出現在 D1、D2，DF = 2
IDF(洗衣機) = log(1 + (3 - 2 + 0.5) / (2 + 0.5))
            = log(1 + 1.5 / 2.5)
            = log(1 + 0.6)
            = log(1.6)
            ≈ 0.470

「訂位」出現在 D1、D3，DF = 2
IDF(訂位) ≈ 0.470（同上，DF 相同）
```

#### 步驟二：計算每份文件的 K

```text
D1（|d|=5）：K₁ = 1.2 × (1 - 0.75 + 0.75 × 5/6.33)
                 = 1.2 × (0.25 + 0.593)
                 = 1.2 × 0.843 = 1.012

D2（|d|=8）：K₂ = 1.2 × (0.25 + 0.75 × 8/6.33)
                 = 1.2 × (0.25 + 0.948)
                 = 1.2 × 1.198 = 1.438

D3（|d|=6）：K₃ = 1.2 × (0.25 + 0.75 × 6/6.33)
                 = 1.2 × (0.25 + 0.711)
                 = 1.2 × 0.961 = 1.153
```

#### 步驟三：計算每個詞對每份文件的貢獻

**詞「洗衣機」：**

```text
D1：TF=1，TF_norm = 1 × 2.2 / (1 + 1.012) = 2.2 / 2.012 ≈ 1.093
    貢獻 = 0.470 × 1.093 ≈ 0.514

D2：TF=2，TF_norm = 2 × 2.2 / (2 + 1.438) = 4.4 / 3.438 ≈ 1.280
    貢獻 = 0.470 × 1.280 ≈ 0.602

D3：TF=0，貢獻 = 0
```

**詞「訂位」：**

```text
D1：TF=1，TF_norm = 1 × 2.2 / (1 + 1.012) = 2.2 / 2.012 ≈ 1.093
    貢獻 = 0.470 × 1.093 ≈ 0.514

D2：TF=0，貢獻 = 0

D3：TF=1，TF_norm = 1 × 2.2 / (1 + 1.153) = 2.2 / 2.153 ≈ 1.022
    貢獻 = 0.470 × 1.022 ≈ 0.480
```

#### 步驟四：加總分數與排名

```text
D1：0.514 + 0.514 = 1.028   ← 兩個詞都有，排第一
D2：0.602 + 0     = 0.602   ← 只有洗衣機（且出現兩次），排第二
D3：0     + 0.480 = 0.480   ← 只有訂位，排第三
```

**排名：D1 > D2 > D3**

D1 因為同時含兩個查詢詞且文件較短，分數最高，符合直覺。

---

### 當 b = 0 時會怎樣？

以 D1 和 D2 對「洗衣機」的貢獻為例：

```text
b=0 → K = k1 = 1.2（所有文件一樣）

D1：TF=1，TF_norm = 2.2 / (1 + 1.2) = 1.000，貢獻 = 0.470
D2：TF=2，TF_norm = 4.4 / (2 + 1.2) = 1.375，貢獻 = 0.646
```

D2 因為詞頻更高（出現兩次）而領先 D1 更多。長度懲罰關閉後，重複一個詞多次的長文件更容易得高分。

## 整合比較

### BM25 vs TF-IDF

| 比較項目 | TF-IDF | BM25 |
|----------|--------|------|
| 詞頻函數 | 線性（TF 越大分數越大） | 飽和型（趨近 k1+1 的上限） |
| 長度正規化 | 無（或用 cosine 正規化） | b 參數控制，可精確調整 |
| IDF 公式 | log(N / DF) | log(1 + (N - DF + 0.5) / (DF + 0.5)) |
| 超參數 | 無 | k1（預設 1.2）、b（預設 0.75） |
| 實驗支持 | 1970 年代 | TREC 實驗反覆驗證，業界首選基線 |
| 實作 | 自行計算 | Elasticsearch / Lucene 預設 |

BM25 在大多數任務上明顯優於 TF-IDF，調整成本低，仍是所有向量方法的對比基線。

### 布林查詢 vs 排名檢索

| 比較項目 | 布林查詢 | 排名檢索（TF-IDF / BM25） |
|----------|----------|---------------------------|
| 輸出格式 | 是或否（符合 / 不符合） | 分數排序的文件列表 |
| 查詢語言 | 精確的 AND / OR / NOT | 自然語言關鍵字 |
| 文件「洗衣機」出現 5 次 | 與出現 1 次完全相同 | 高頻得分更高（但有飽和上限） |
| 長文件天然優勢 | 無懲罰 | BM25 的 b 參數做長度正規化 |
| 適合場景 | 法規條款精確匹配、代碼查詢 | 開放式問答、相似度排名 |
| 解釋性 | 極高（能說出哪個條件不符合） | 中（可追 IDF、TF 貢獻） |

### 稀疏檢索的優缺點與適用場景

**適合用稀疏檢索（BM25）的情況：**
- 訂位代碼、航班號、法規條款編號等精確術語
- 稀有的專有地名（如「薩爾斯堡中央車站」）
- 語言資源少、無法訓練 embedding 的情境

**BM25 的失敗模式（稀疏檢索的共同弱點）：**
- **同義詞漏檢：** 查「烘衣設備」找不到只寫「烘衣機」的文件
- **跨語言：** 中文查詢無法匹配英文文件
- **切詞錯誤：** 「洗烘衣機」切成「洗烘」＋「衣機」，查「洗衣機」找不到
- **否定語意：** 「不含早餐」和「含早餐」對「早餐」這個詞的 BM25 分數相同

**SPLADE 的位置：** 用 Transformer 為詞彙產生權重，讓原文未出現的同義詞也能有貢獻，同時保留倒排索引的查詢速度。代價是額外的模型推論與索引膨脹（index bloat）。

## 習題

**題 1（機制）：** 說明為什麼移除停用詞「不」在取消政策類文件中可能造成問題？

<details>
<summary>解答</summary>

「不可取消」和「可取消」在移除「不」之後，索引內只剩下「可」和「取消」，兩份意義相反的文件會有相同的 posting list，布林查詢「取消 AND 可」會同時回傳兩者。應用程式必須在後段用語意理解或 NLI 模型再區分，或乾脆不把「不」列為停用詞。

</details>

**題 2（手算）：** 給定以下兩份文件，建出「夜車」和「薩爾斯堡」的 posting list，並執行「夜車 AND 薩爾斯堡」查詢。

```
D1：夜車 從 維也納 出發 抵達 薩爾斯堡
D2：薩爾斯堡 的 旅館 提供 夜車 接駁 服務
D3：維也納 旅館 早餐 自助
```

<details>
<summary>解答</summary>

D1：夜車(0) 維也納(1) 出發(2) 抵達(3) 薩爾斯堡(4)

</details>

**題 3（手算 BM25）：** 假設 N=3，兩份文件都只提一次「烘衣機」（DF=2），文件長度分別是 2 和 6，avgdl=4，k1=1.2，b=0.75。算兩份文件對「烘衣機」的 BM25 分數（IDF × TF_norm），並說明為何短文件得分較高。

<details>
<summary>解答</summary>

```text
IDF = log(1 + (3 - 2 + 0.5) / (2 + 0.5)) = log(1.6) ≈ 0.182

D_short（|d|=2）：
  K = 1.2 × (1 - 0.75 + 0.75 × 2/4) = 1.2 × (0.25 + 0.375) = 1.2 × 0.625 = 0.75
  TF_norm = 1 × 2.2 / (1 + 0.75) = 2.2 / 1.75 ≈ 1.257
  score = 0.182 × 1.257 ≈ 0.229

D_long（|d|=6）：
  K = 1.2 × (0.25 + 0.75 × 6/4) = 1.2 × (0.25 + 1.125) = 1.2 × 1.375 = 1.65
  TF_norm = 1 × 2.2 / (1 + 1.65) = 2.2 / 2.65 ≈ 0.830
  score = 0.182 × 0.830 ≈ 0.151
```

短文件（0.229）高於長文件（0.151）。理由：同樣是「出現一次」，在短文件中這個詞的相對密度更高，b 參數讓 K 較小，使 TF_norm 較大。如果設 b=0，兩份文件的分數都等於 0.182 × 1.0 = 0.182，完全相同。

</details>

**題 4（選型）：** 一個旅遊問答系統發現：BM25 把「薩爾斯堡 Airbnb 規定」這筆查詢的前三名全排給含有大量「薩爾斯堡」的旅遊指南頁，而不是真正寫了 Airbnb 規定的那一份文件。可能的原因是什麼？你會怎麼調整？

<details>
<summary>解答</summary>

可能原因：「Airbnb」和「規定」在語料庫中很稀有（IDF 高），但旅遊指南頁字數多，「薩爾斯堡」多次出現，TF × (k1+1) / (TF+K) 累積起來高於含「Airbnb 規定」但「薩爾斯堡」只出現一次的文件。

調整方向：
1. 降低 b（減少長度懲罰），讓長文件不那麼有利。
2. 把「Airbnb 規定」這樣的稀有詞欄位提高欄位權重。
3. 在前處理確認「Airbnb」沒有被切詞工具切壞（例如切成「Air」「bnb」）。
4. 若語意仍無法對齊，考慮混合 BM25 + dense retrieval。

</details>
