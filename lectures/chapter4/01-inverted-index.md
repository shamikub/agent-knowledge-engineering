# 4.1 從字元到倒排索引

## 學習目標

讀完本節後，你應該能：

- 手動對三份文件建立一個包含 (doc_id, freq, positions) 的倒排索引
- 說明 posting list 的結構，以及為什麼每個欄位都有用
- 解釋 stopwords 和 stemming 的作用與代價
- 用 AND（merge）和 OR（union）兩種操作執行布林查詢
- 說明布林查詢與排名檢索（TF-IDF / BM25）的本質差異

**先備知識：** 集合的交集與聯集運算。

---

## 為什麼不直接掃描每份文件？

想像你在旅行前整理了三百封 email，要找「有提到洗衣機」的信。最直接的做法是從第一封讀到最後一封。這叫做**線性掃描（linear scan）**，查詢時間與文件數成正比。

書本的末頁索引解決了同樣的問題：它把「每個詞出現在哪一頁」預先整理好，查詢時直接翻到那一頁，不需要重讀全書。

電腦的**倒排索引（inverted index）**就是這個想法的實作：

- **正向索引（forward index）**：文件 → 它包含哪些詞（書本內容）
- **倒排索引（inverted index）**：詞 → 哪些文件包含它（書末索引）

建索引在事前做一次，查詢時只需走兩個詞的 posting list 再合併，速度與**匹配文件數**成正比，而非與**全部文件數**成正比。這是搜尋引擎能在毫秒內回答的原因。

## 任務定義

| 項目 | 說明 |
|------|------|
| 輸入 | 文件集合 D = {d₁, d₂, …, dₙ}，每份已切詞成 token 序列 |
| 輸出 | 映射 term → posting list；每筆 posting 為 (doc_id, freq, positions) |
| 子任務 | 分詞、正規化、建索引、查詢執行 |
| 常見基線 | Elasticsearch / Lucene 的預設分析器 |

**符號說明：**

- `t`：詞（term）
- `d`：文件（document）
- `freq(t, d)`：詞 t 在文件 d 中出現的次數
- `positions(t, d)`：詞 t 在文件 d 中出現的位置列表（以 token 序號計）

---

## 架構：從原始文字到 posting list

整個建索引流程分為四步。每步的輸出就是下一步的輸入。

```
原始文字
   ↓
1. 分詞（Tokenization）
   ↓
2. 正規化（Normalization）
   ├── 轉小寫（lowercase）
   ├── 詞幹化（stemming）或詞形還原（lemmatization）
   └── 移除停用詞（stopwords removal）
   ↓
3. 建 Posting List
   ↓
4. 布林查詢執行（AND = merge / OR = union）
```

### 步驟一：分詞

中文沒有空格，需要先用切詞工具（如 jieba、ckip-transformers）切出詞的邊界。英文以空格和標點為界較容易，但「check-in」要算一個詞還是兩個詞，取決於應用需求。

**切詞粒度的影響：**「洗烘衣機」如果切成「洗烘」＋「衣機」，查詢「洗衣機」就永遠找不到這份文件。

### 步驟二：正規化

**轉小寫：** 讓「Hotel」和「hotel」視為同一個詞。代價：專有名詞「APPLE」（公司）和「apple」（水果）被合併。

**詞幹化（stemming）：** 把「running」、「runs」、「ran」都化為詞根「run」。英文常用 Porter Stemmer；中文通常不需要，因為詞形變化少。代價：過度化簡可能把不同意思的詞合併（over-stemming）。

**停用詞（stopwords）：** 移除「的」「是」「在」「and」「the」等高頻但幾乎無辨識力的詞，以縮小索引大小、加快查詢。代價：「不 可 取消」裡的「不」如果被移除，布林查詢就無法區分「可取消」與「不可取消」。**在法律與條款類文件要特別小心。**

### 步驟三：建 Posting List

對每個正規化後的 token，將 (doc_id, position) 記錄到該詞的 posting list。最後統計每份文件的出現次數 freq。

### 步驟四：布林查詢執行

- **AND（交集 / merge）：** 走兩個 posting list，以雙指針找共同的 doc_id。只回傳同時出現兩個詞的文件。
- **OR（聯集 / union）：** 走兩個 posting list，合併所有 doc_id。
- **NOT：** 在 AND 後排除某個詞的文件，需要整份文件集合當背景。

## 完整算例：手建倒排索引

### 原始文件

```
D1（訂位確認信）：「您的訂位已確認，住宿含早餐，不含洗衣機服務。」
D2（取消政策）：「取消訂位需在入住前 48 小時辦理，逾期不予退款。」
D3（住宿說明）：「本房型提供洗衣機與烘衣機，洗烘費用另計。」
```

### 步驟一：切詞後（簡化示意，移除標點）

```
D1：您 的 訂位 已 確認 住宿 含 早餐 不含 洗衣機 服務
D2：取消 訂位 需 在 入住 前 48 小時 辦理 逾期 不予 退款
D3：本 房型 提供 洗衣機 與 烘衣機 洗烘 費用 另計
```

### 步驟二：正規化（移除停用詞「的」「已」「在」「與」「本」）

```
D1（pos 從 0 起）：訂位(0) 確認(1) 住宿(2) 含(3) 早餐(4) 不含(5) 洗衣機(6) 服務(7)
D2：取消(0) 訂位(1) 需(2) 入住(3) 前(4) 48(5) 小時(6) 辦理(7) 逾期(8) 不予(9) 退款(10)
D3：房型(0) 提供(1) 洗衣機(2) 烘衣機(3) 洗烘(4) 費用(5) 另計(6)
```

### 步驟三：倒排索引（term → posting list）

| Term   | Posting list（doc_id, freq, positions）           |
|--------|---------------------------------------------------|
| 訂位   | (D1, 1, [0])、(D2, 1, [1])                        |
| 確認   | (D1, 1, [1])                                      |
| 住宿   | (D1, 1, [2])                                      |
| 不含   | (D1, 1, [5])                                      |
| 洗衣機 | (D1, 1, [6])、(D3, 1, [2])                        |
| 取消   | (D2, 1, [0])                                      |
| 入住   | (D2, 1, [3])                                      |
| 退款   | (D2, 1, [10])                                     |
| 烘衣機 | (D3, 1, [3])                                      |
| 洗烘   | (D3, 1, [4])                                      |

### 步驟四：執行布林查詢

**查詢 A：「洗衣機 AND 烘衣機」**

```
洗衣機 → [D1, D3]
烘衣機 → [D3]

雙指針 merge：
  D1 vs D3：D1 < D3，左指針前進
  D3 vs D3：相同 → 加入結果
結果：[D3]
```

回傳 D3（住宿說明）。正確：只有 D3 同時提到這兩個詞。

**查詢 B：「洗衣機 OR 烘衣機」**

```
洗衣機 → [D1, D3]
烘衣機 → [D3]

union：[D1, D3]
```

回傳 D1 和 D3。

## 反例：「烘衣」和「烘衣機」是不同的 term

現在加入一份新文件：

```
D4（設備補充說明）：「本館提供洗烘設備，烘衣功能需預約。」
切詞後：洗烘(0) 設備(1) 烘衣(2) 功能(3) 需(4) 預約(5)
```

此時：
- `烘衣機` 的 posting list：(D3, 1, [3])
- `烘衣` 的 posting list：(D3, 1, [4])、(D4, 1, [2])

執行「洗衣機 AND 烘衣機」：**D4 不在結果中**，因為 D4 裡的詞是「烘衣」而非「烘衣機」。

這就是**術語不匹配（vocabulary mismatch）**問題：語意相近但字面不同的詞，倒排索引無法自動橋接。解法包括：
- 加入同義詞表（synonym expansion）：在索引時或查詢時把「烘衣」擴展為「烘衣機」
- 改用向量檢索（見 4.3 節）捕捉語意相似度

## 方法比較：布林查詢 vs 排名檢索

| 比較項目 | 布林查詢 | 排名檢索（TF-IDF / BM25） |
|----------|----------|---------------------------|
| 輸出格式 | 是或否（符合 / 不符合） | 分數排序的文件列表 |
| 查詢語言 | 精確的 AND / OR / NOT | 自然語言關鍵字 |
| 文件「洗衣機」出現 5 次 | 與出現 1 次完全相同 | 高頻得分更高（但有飽和上限） |
| 長文件天然優勢 | 無懲罰 | BM25 的 b 參數做長度正規化 |
| 適合場景 | 法規條款精確匹配、代碼查詢 | 開放式問答、相似度排名 |
| 解釋性 | 極高（能說出哪個條件不符合） | 中（可追 IDF、TF 貢獻） |

**TF-IDF 預覽：** 下一節 BM25 是從 TF-IDF 改進而來。核心思路是讓「稀有詞出現多次」比「常見詞出現多次」得到更高分，並避免長文件只因為字數多而佔優。

## 習題

**題 1（機制）：** 說明為什麼移除停用詞「不」在取消政策類文件中可能造成問題？

<details>
<summary>解答</summary>

「不可取消」和「可取消」在移除「不」之後，索引內只剩下「可」和「取消」，兩份意義相反的文件會有相同的 posting list，布林查詢「取消 AND 可」會同時回傳兩者。應用程式必須在後段用語意理解或 NLI 模型再區分，或乾脆不把「不」列為停用詞。

</details>

**題 2（手算）：** 給定以下兩份文件，建出「夜車」和「薩爾斯堡」的 posting list，並執行「夜車 AND 薩爾斯堡」查詢。

```
D1：夜車 從 維也納 出發 抵達 薩爾斯堡
D2：薩爾斯堡 的 旅館 提供 夜車 接駁 服務
D3：維也納 旅館 早餐 自助
```

<details>
<summary>解答</summary>

切詞（移除「從」「的」）：

```
D1：夜車(0) 維也納(1) 出發(2) 抵達(3) 薩爾斯堡(4)
D2：薩爾斯堡(0) 旅館(1) 提供(2) 夜車(3) 接駁(4) 服務(5)
D3：維也納(0) 旅館(1) 早餐(2) 自助(3)
```

Posting list：
- 夜車 → (D1, 1, [0])、(D2, 1, [3])
- 薩爾斯堡 → (D1, 1, [4])、(D2, 1, [0])

執行 AND（merge）：
- D1 vs D1 → 相同，加入結果
- D2 vs D2 → 相同，加入結果
結果：[D1, D2]

D3 不含任一詞，不出現在結果中。

</details>

**題 3（選型）：** 一個航空訂位系統想查詢「PNR 代碼 ABC123 的行程」。你會選擇布林查詢還是排名檢索？為什麼？

<details>
<summary>解答</summary>

選布林查詢（或精確匹配）。理由：PNR 代碼是不能有歧義的精確字串，不需要「相似度」，只需要「完全符合」。若使用排名檢索，「ABC124」可能因為字面相似而排到前幾名，反而造成混淆。精確匹配可用倒排索引的 AND 查詢，或在資料庫用等號過濾。排名檢索適合用在「行程概述相似的案例」這類開放式問句。

</details>
