# 4.4 從候選到重排

## 學習目標

讀完本節後，你應該能：

- 說明為什麼兩階段（粗排 + 精排）比單一階段更有效率且更精確

- 說明「top-k 裡沒有答案，cross-encoder 無法補救」這個根本限制

**先備知識：** 4.2 節 BM25、4.3 節 bi-encoder 與向量檢索。

## 任務定義：為何需要兩階段？

假設語料庫有 100 萬份文件，使用者問「取消訂位的退款期限是幾天？」。

**單階段 cross-encoder：** 把查詢和每份文件配對，算 100 萬次前向傳播。在 GPU 上每次約 10ms → 總計 10,000 秒。不可行。

**兩階段漏斗（two-stage pipeline）：**

```
100 萬份文件
   ↓ 粗排（Retriever）：BM25 / bi-encoder，速度快
top-100 候選
   ↓ 精排（Reranker）：cross-encoder，速度慢但精確
top-10 最終結果
```

粗排把候選壓縮到幾十或幾百份，讓精排的計算量變得可行。兩階段的總成本遠低於單階段 cross-encoder，同時精確度優於單階段 bi-encoder。

**核心邏輯：** 粗排的任務是「召回（recall）」——不能漏掉重要文件；精排的任務是「排序（precision）」——把最相關的放在前面。

## Cross-encoder 完整說明

### 輸入格式

Cross-encoder 把查詢和文件**串接**成一個序列送入 Transformer：

```
[CLS] 查詢文字 [SEP] 文件文字 [SEP]
```

例如：
```
[CLS] 取消訂位退款期限是幾天 [SEP] 訂位取消需在入住前 48 小時辦理，逾期不予退款 [SEP]
```

整個序列做完整的 self-attention，讓查詢的每個 token 能直接注意到文件的每個 token。最後用 [CLS] 的隱藏狀態接一個線性層，輸出相關性分數（通常是 0 到 1 的概率）。

### 為何比 bi-encoder 更精確？

Bi-encoder 的問題：查詢和文件各自獨立編碼，兩者的 token 在 pooling 之前從未互相「見面」。細粒度的詞語對齊資訊（例如「退款」和「不予退款」的否定關係）在壓縮成一個向量時丟失了。

Cross-encoder 允許 query token 和 document token 完整互相注意，能辨認出：
- 否定關係（「不可取消」vs「可取消」）
- 條件關係（「限入住 3 晚以上」）
- 兩個條件同時成立（「能洗也能烘」）

### 推論成本

| 情境 | 計算次數 | 說明 |
|------|----------|------|
| Bi-encoder（文件） | 1 次 / 文件（離線預算） | 可預計算並快取 |
| Bi-encoder（查詢） | 1 次 / 查詢 | 線上即時計算 |
| Cross-encoder | k 次 / 查詢（k = 候選數） | 無法預計算，每對都要重跑 |

**實際部署：** Cross-encoder 通常只跑在 top-20 到 top-100 的候選上。若 GPU 吞吐量不足，可用知識蒸餾（knowledge distillation）訓練一個小型 cross-encoder，或改用 ColBERT 的 MaxSim 近似。

## Reciprocal Rank Fusion（RRF）完整算例

RRF 解決「如何融合來自不同系統的排名」而不需要校準各系統的分數尺度（BM25 的分數和 cosine 相似度的量級完全不同）。

### 公式

對文件 d 在系統 s 的排名 rank_s(d)，RRF 分數為：

```
RRF(d) = Σ_s  1 / (c + rank_s(d))
```

其中 c 是平滑常數，預設 c = 60。

**c 的作用：** 避免第 1 名獨大。若 c = 0，第 1 名得 1/1 = 1.0，第 2 名得 1/2 = 0.5，差距極大。c = 60 後，第 1 名得 1/61 ≈ 0.0164，第 2 名得 1/62 ≈ 0.0161，差距大幅縮小。兩個系統都把文件排在前面，遠比一個系統的第 1 名更有優勢。

### 完整算例

**三個系統，各自對五份文件的排名：**

```
系統 A（BM25）：     D1(1) > D2(2) > D3(3) > D4(4) > D5(5)
系統 B（bi-encoder）：D2(1) > D3(2) > D4(3) > D1(4) > D5(5)
系統 C（SPLADE）：   D3(1) > D1(2) > D5(3) > D2(4) > D4(5)
```

**計算每份文件的 RRF 分數（c = 60）：**

```
D1：1/(60+1) + 1/(60+4) + 1/(60+2)
  = 1/61 + 1/64 + 1/62
  = 0.01639 + 0.01563 + 0.01613
  = 0.04815

D2：1/(60+2) + 1/(60+1) + 1/(60+4)
  = 1/62 + 1/61 + 1/64
  = 0.01613 + 0.01639 + 0.01563
  = 0.04815

D3：1/(60+3) + 1/(60+2) + 1/(60+1)
  = 1/63 + 1/62 + 1/61
  = 0.01587 + 0.01613 + 0.01639
  = 0.04839

D4：1/(60+4) + 1/(60+3) + 1/(60+5)
  = 1/64 + 1/63 + 1/65
  = 0.01563 + 0.01587 + 0.01538
  = 0.04688

D5：1/(60+5) + 1/(60+5) + 1/(60+3)
  = 1/65 + 1/65 + 1/63
  = 0.01538 + 0.01538 + 0.01587
  = 0.04663
```

**RRF 最終排名：D3(0.04839) > D1 ≈ D2(0.04815) > D4(0.04688) > D5(0.04663)**

**解讀：** D3 被三個系統都排在前三名（系統 A 第 3、系統 B 第 2、系統 C 第 1），因此在 RRF 中脫穎而出。D1 被系統 A 排第 1 但系統 B 排第 4，兩者互相抵消，最後與 D2 並列。

## 反例：top-k 裡沒有答案，cross-encoder 無法補救

假設正確答案是 D6（取消政策的第 3 段），但由於 BM25 的詞彙不匹配（文件使用「撤銷訂單」而非「取消訂位」），D6 在第一階段排名第 23，只取 top-20 候選時 D6 不在候選集中。

```
第一階段（BM25 top-20）：D1, D2, D3, ..., D20  ← D6 不在此！
     ↓
Cross-encoder 重排 top-20
     ↓
最終排名：D1, D3, D7, ...  ← D6 永遠不會出現
```

**Cross-encoder 無法憑空創造候選。** 若答案不在粗排的 top-k 裡，精排再精確也無濟於事。

**修復方向（往上游）：**
1. 擴大粗排的 top-k（從 20 改到 50），增加召回機會
2. 加入同義詞擴展（synonym expansion），讓「撤銷訂單」也能命中「取消訂位」的索引
3. 加入另一條向量檢索路徑，以 RRF 融合，彌補 BM25 的詞彙不匹配
4. 在文件前處理時加入 metadata（例如「synonyms: 取消, 撤銷, 退訂」），讓索引更豐富

## 三層漏斗的精度/召回/成本

```
層次        方法           候選數        Recall  Precision  延遲
─────────────────────────────────────────────────────────────
第一層      BM25           100萬 → 100   高      低         ~5ms
第一層      Bi-encoder     100萬 → 100   高      中         ~20ms
（或融合）  BM25 + RRF     100萬 → 100   最高    低         ~25ms
─────────────────────────────────────────────────────────────
第二層      Cross-encoder  100 → 10      ─      高         ~200ms
─────────────────────────────────────────────────────────────
```

**選型口訣：**
- 答案型查詢（代碼、法條）→ BM25 為主
- 語意型查詢（口語、改寫）→ Bi-encoder 為主
- 兩種錯誤都有 → BM25 + Bi-encoder + RRF
- 候選已齊但順序不佳 → 加 Cross-encoder
- 要細粒度詞匹配且可接受更大索引 → ColBERT

---

## 方法比較表

| 需求 | 優先試哪一種 | 怎麼知道該換 |
|------|-------------|--------------|
| 查航班代碼、規則用語 | BM25 | 測別名與自然語言改寫的 Recall@k |
| 用口語找相近段落 | 小型多語 E5 | 看精確代碼與否定條件是否掉排名 |
| 兩種錯誤各有互補 | BM25 + E5 + RRF | 同 k 回報完整證據命中與延遲 |
| 候選已齊，順序不佳 | Cross-encoder | 同候選集量排序差異和單案成本 |
| 想保留細粒度詞匹配 | ColBERT | 比排序收益、索引大小和查詢時間 |

## 習題

**題 1（手算）：** 兩個系統 A 和 B 對文件 X、Y、Z 的排名如下：A 排名為 X(1)、Y(2)、Z(3)；B 排名為 Y(1)、Z(2)、X(3)。用 c=60 計算三份文件的 RRF 分數，並說明最終排名。

<details>
<summary>解答</summary>

```
X：1/(60+1) + 1/(60+3) = 1/61 + 1/63 = 0.01639 + 0.01587 = 0.03226
Y：1/(60+2) + 1/(60+1) = 1/62 + 1/61 = 0.01613 + 0.01639 = 0.03252
Z：1/(60+3) + 1/(60+2) = 1/63 + 1/62 = 0.01587 + 0.01613 = 0.03200
```

最終排名：**Y(0.03252) > X(0.03226) > Z(0.03200)**

Y 被兩個系統都排在前兩名（A 第 2、B 第 1），綜合表現最穩定，所以 RRF 把它排第一。X 雖然在 A 是第 1，但在 B 只有第 3，被平均拉低了。

</details>

**題 2（概念）：** 一個旅遊問答系統使用 BM25 取 top-10 再用 cross-encoder 重排。使用者反映「取消政策的例外條款總是找不到」。你懷疑答案在 BM25 的第 15 名。說明你的診斷步驟和修復方案。

<details>
<summary>解答</summary>

**診斷步驟：**

1. **確認 oracle retrieval：** 把已知的正確答案文件 ID 手動加入候選集，讓 cross-encoder 重排，確認它能排到第 1 名 → 若可以，則問題確實在第一階段召回，而非 cross-encoder 本身。

2. **量化召回邊界：** 測試 Recall@5、Recall@10、Recall@20，確認答案出現在 top-15 而非 top-10。

3. **分析 BM25 失敗原因：** 查看例外條款的文字，找出是否有詞彙不匹配（例如「豁免」vs「例外」、「不適用」vs「除外」）。

**修復方案：**

1. 把粗排的 top-k 從 10 擴大到 20 或 50（最直接）。
2. 在 BM25 加同義詞表（「例外」→ 展開「豁免」「特殊情況」「除外條款」）。
3. 加一條 bi-encoder 路徑，以 RRF 融合，讓語意匹配彌補詞彙不匹配。
4. 若例外條款在不同文件（例如主條款 + 附件），考慮多跳查詢（見 4.5 節）。

</details>

---

**題 3（選型）：** 你有一個語料庫，BM25 的 Recall@20 已達 0.95，但 Precision@3 只有 0.40（前三名有很多不相關文件）。你是否需要加 cross-encoder？說明理由和預期效果。

<details>
<summary>解答</summary>

**需要加 cross-encoder。** 理由：

- Recall@20 = 0.95 代表「答案幾乎都在前 20 名裡」→ 粗排的召回沒問題，答案確實在候選集中。
- Precision@3 = 0.40 代表「前三名有 60% 是不相關文件」→ 排序（ordering）的問題，不是召回問題。

這是 cross-encoder 最適合的場景：候選已齊，只需要重新排序，讓最相關的文件移到前面。

預期效果：Cross-encoder 對 top-20 重排後，Precision@3 有望提升到 0.70 以上（實際提升幅度取決於任務複雜度和 cross-encoder 的訓練資料）。

注意：如果 Recall@20 本身只有 0.60，加 cross-encoder 也無法解決召回問題，要先修粗排。

</details>
