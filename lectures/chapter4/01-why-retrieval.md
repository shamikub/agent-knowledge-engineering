# 4.1 為什麼不能直接把所有知識送給 LLM

[章節導覽](intro.md) · [下一節](02-sparse-retrieval.md)

---

## 學習目標

完成本節後，你能夠：

1. 計算一個知識庫的概略 token 量，並對照常見模型的 context window 上限。
2. 說明 context window 限制帶來的成本、延遲與「Lost in the Middle」效應。
3. 比較三種壓縮策略（抽取式摘要、RAPTOR、LongLLMLingua）在例外條件保留率上的取捨。
4. 解釋為何壓縮無法完全取代檢索，以及本章要解決的核心問題是什麼。

**先備知識：** 知道 LLM 有 context window（上下文視窗）限制即可。不需要事先了解向量嵌入。

---

## 1. Context Window 的現實

### 1.1 token 量估算

現代 LLM 的 context window 通常以 tokens 計量。一個粗略的換算基準：中文約每字 1–2 tokens，英文約每個單字 1–1.5 tokens。

以一個中型企業的知識庫為例：

```
旅遊政策手冊：  50 頁  × 500 字/頁 ≈  25,000 tokens
訂位確認信：   200 封  × 300 字/封 ≈  60,000 tokens
旅館條款文件：  30 份  × 800 字/份 ≈  24,000 tokens
─────────────────────────────────────────────────
合計                             ≈ 109,000 tokens
```

GPT-4o 的 context window 是 128,000 tokens——勉強放得下，但這只是一個中型知識庫。若文件庫成長到數千份，或需要加入即時更新的票價與規定，就立刻超出限制。

### 1.2 成本與延遲隨 token 數線性成長

即使模型支援大 context，也不代表「能放就放」：

- **成本：** 大多數 API 按 token 計費。把 109,000 tokens 全送進去，每次查詢的費用是只送 2,000 tokens 的 54 倍。
- **延遲：** Transformer 的注意力機制是 O(n²) 計算，context 越長，推論越慢。
- **速率限制：** 許多服務對每分鐘的 token 吞吐量有上限，大 context 請求更容易觸頂。

### 1.3 Lost in the Middle 效應

Liu et al.（2023）的研究顯示，即使把所有文件都放進 context，模型對位於 **中段** 的資訊回答準確率明顯低於開頭或結尾的資訊。

```
                 正確率（示意）
100% |  *                              *
 80% |     *                        *
 60% |        *                  *
 40% |           *   *   *   *
 20% |
  0% +─────────────────────────────────→
     位置  開頭              結尾
```

把知識庫全送進去，不代表模型能「讀到」每一個細節。位於中間的「21:00 前入住」這個關鍵例外條件，可能就這樣被忽略。

---

## 2. 三種應對方式

面對「知識量 >> context window」這個矛盾，有三條路：

| 策略 | 核心思路 | 適用情境 |
|------|----------|----------|
| **壓縮** | 把長文縮短再送進去 | 文件數量少、問題類型多樣 |
| **檢索** | 只送與查詢相關的片段 | 文件庫大、查詢意圖明確 |
| **兩者結合** | 先檢索候選片段，再壓縮後送入 | 大型知識庫 + 緊張的 token 預算 |

本節先深入「壓縮」的三種方法，理解其能力極限；本章其餘節則專注於「檢索」的各種技術。

---

## 3. 壓縮的三種方法

**任務定義：** 給定長文件（政策條款、訂位確認信、旅遊手冊），在固定 token 預算下，保留讓 LLM 能正確回答後續問題的關鍵細節。

**核心張力：** 壓縮比越高，省越多 tokens，但遺失關鍵細節的風險也越高。重要的不只是「壓了多少」，而是「保留了哪些關鍵資訊」。

**衡量指標：**
- **壓縮比（compression ratio）：** `1 - (壓縮後 tokens / 原始 tokens)`
- **例外條件保留率（exception retention rate）：** 壓縮後版本中，原文關鍵例外句子的保留比例
- **任務成功率（task success rate）：** 以壓縮後版本為上下文，LLM 回答問題的正確率

### 3.1 抽取式摘要（Extractive Summarization）

**原理：** 從原文選出最重要的句子，直接拼接成摘要，不改寫文字。

```
原文：
1. 入住截止時間為晚間 21:00。
2. 旅客須提前與旅館聯繫若無法按時抵達。
3. 旅館訂房包含早餐。
4. 健身房開放時間為 06:00–22:00。
5. 取消政策：7天前免費，3天前50%退款。

抽取式摘要（選句 1, 5）：
入住截止時間為晚間 21:00。取消政策：7天前免費，3天前50%退款。
```

**優點：** 句子來自原文，不會引入幻覺（hallucination）。

**缺點：** 選句依賴重要性評分，若「21:00 前入住」被評為低分（例如文件主題是取消政策），這句話可能被丟棄。

### 3.2 RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）

**核心思想：** 把文件分成段落 → 嵌入向量 → 聚類 → 對每個群組生成摘要 → 遞迴對上層摘要再聚類，建立多層索引樹。

```
層級 2（全域摘要）：
  "薩爾斯堡旅遊住宿取消政策及設施說明"

層級 1（主題摘要）：
  群組 A：入住規則（截止 21:00、晚到通知）
  群組 B：取消費率（7天/3天/1天）
  群組 C：設施（早餐、健身房）

層級 0（原始段落）：
  §1 §2 §3 §4 §5 ...
```

**查詢邏輯：**
- 廣泛問題（「這家旅館有什麼政策？」）→ 在層級 1–2 找答案
- 細節問題（「幾點前要入住？」）→ 從層級 1 的群組 A 下鑽到層級 0

**優點：** 同時支援摘要層級與細節層級的查詢。

**缺點：** 建索引成本高（需要多次 LLM 呼叫）；若聚類把例外條件（如 21:00 截止）歸入錯誤群組，查詢細節時可能找不到。

**論文：** Sarthi et al., "RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval," ICLR 2024. arXiv:2401.18059

### 3.3 LongLLMLingua（動態壓縮）

**核心思想：** 在已取得相關段落後，依照問題相關性動態裁剪每個句子，只保留與問題直接相關的 tokens。

```
問題：「我明晚 21:30 才能到，可以入住嗎？」

LongLLMLingua 分析相關性：
  "入住截止時間為晚間 21:00" → 高相關 → 保留
  "健身房開放 06:00–22:00"   → 低相關 → 刪除
  "旅館訂房包含早餐"         → 低相關 → 刪除
```

**優點：** 針對特定問題最佳化，保留率最高。

**缺點：** 每個問題都要重新壓縮，不能預先建索引；若問題表述不清，相關性評分可能誤刪關鍵資訊。

**論文：** Jiang et al., "LongLLMLingua: Accelerating and Enhancing LLMs in Long Context Scenarios via Prompt Compression," ACL 2024. arXiv:2310.06839

## 4. 完整算例：「21:00 前入住」的例外條件

### 4.1 原始文件

```
Hotel Amadeus 住宿條款（120 tokens）

[1] 標準入住時間為下午 15:00 至晚間 21:00。
[2] 旅客若預計在 21:00 後抵達，須於入住日前致電旅館確認。
[3] 旅館於確認後可安排延後入住，不另收費。
[4] 未事先確認而在 21:00 後抵達者，旅館有權取消訂房。
[5] 退房時間為上午 11:00，延遲退房須加收 50% 日費。
[6] 旅館提供行李寄存服務至晚間 22:00。
[7] 取消政策：入住日前 7 天（含）以前取消，全額退款。
[8] 入住日前 3 至 6 天取消，退款 50%。
[9] 入住日前 1 至 2 天取消，退款 20%。
[10] 當天取消或未到（no-show），不退款。
```

**正確回答需要的句子：** [1]、[2]、[3]、[4]（共 4 句，含「21:00」這個關鍵截止時間與後續處理流程）

### 4.2 壓縮到 45 tokens 的三種結果

**方法 A：直接截斷（選前 45 tokens）**

```
標準入住時間為下午 15:00 至晚間 21:00。旅客若預計在 21:00 後抵達，須於入住日前致電旅館確認。旅館於確認後...
```

保留句：[1]、[2]、部分[3]。**遺漏** [4]（未事先確認的後果）。
例外條件保留率：3/4 = **75%**。

**方法 B：抽取式摘要（選重要性最高的句子）**

若重要性評分以取消費率為主軸，選出 45 tokens 的摘要：

```
取消政策：7天前全額退款，3–6天退50%，1–2天退20%，當天不退款。
```

保留句：[7]–[10]。**完全遺漏** [1]、[2]、[3]、[4]。
例外條件保留率：0/4 = **0%**。任務**失敗**。

**方法 C：LongLLMLingua（依問題相關性壓縮）**

```
入住截止 21:00。21:00 後抵達須致電確認。確認後可延後入住。未確認者旅館可取消訂房。
```

保留句：[1]、[2]、[3]、[4]（關鍵語意全保留，只壓縮措辭）。
例外條件保留率：4/4 = **100%**。任務**成功**。

### 4.3 token 預算比較表

| Token 預算 | 壓縮比 | 直接截斷保留率 | 抽取式保留率 | LongLLMLingua 保留率 |
|-----------|--------|---------------|-------------|----------------------|
| 2048      | 0%（全文）| 100%        | 100%        | 100%                 |
| 512       | 57%    | 100%          | 50%         | 100%                 |
| 128       | 83%    | 75%           | 25%         | 100%                 |
| 45        | 62.5%  | 75%           | 0%          | 100%                 |
| 20        | 83%    | 0%            | 0%          | 75%                  |

## 5. 壓縮的根本限制

少了「21:00 前入住」這句話，任務就失敗——這個例子揭示了壓縮策略的共同弱點：**壓縮器不知道哪個句子對下一個問題最關鍵**。

三種方法的失效原因各不相同：

| 方法 | 失效根本原因 |
|------|------------|
| 抽取式摘要 | 重要性評分與問題無關，離線決定選哪句 |
| RAPTOR | 聚類錯誤可能把例外條件丟進錯誤的群組 |
| LongLLMLingua | 問題措辭不清時，相關性評分失準 |

更根本的問題是：當 token 預算極小（如 20 tokens）時，所有壓縮方法都難以保留完整語意。**此時應該換策略——只送最相關的片段，而非壓縮整份文件。** 這就是為什麼需要「檢索」。

---

## 6. 結論：這一章要學的是什麼

壓縮是在「已有全部文件」的前提下，讓它塞進 context window。但如果文件庫有 10 萬份文件，壓縮前的第一步必須是：**找出哪幾份文件跟這個問題有關**。

這個「只拿你需要的那部分」的能力，就是本章其餘節的主題：

- **4.2** 稀疏檢索：用倒排索引和 BM25 做字面匹配
- **4.3** 稠密檢索：用向量嵌入捕捉語意相似度
- **4.4** 重排與融合：整合多路訊號，精煉候選
- **4.5** RAG：把檢索到的片段送進 LLM，驗收回答品質

## 7. 習題

**題 1（計算）：** 一個旅遊平台有以下知識庫：旅館合約 200 份（每份平均 1,500 字）、FAQ 文件 50 份（每份平均 400 字）、即時票價更新 1,000 筆（每筆平均 80 字）。假設中文平均每字 1.5 tokens，計算總 token 量，並說明這個知識庫能否直接送入 128k context window 的模型。如果不能，需要壓縮到什麼比例？

<details><summary>解答</summary>

```
旅館合約：200 × 1,500 × 1.5 = 450,000 tokens
FAQ 文件：  50 × 400   × 1.5 =  30,000 tokens
即時票價：1,000 × 80   × 1.5 = 120,000 tokens
─────────────────────────────────────────────
合計：                          600,000 tokens
```

600,000 tokens 遠超過 128k context window（128,000 tokens），無法直接送入。

需要壓縮到的比例：128,000 / 600,000 ≈ **21.3%**，也就是壓縮比至少要 78.7%。

在這麼高的壓縮比下，任何壓縮策略都很難保留所有例外條件。**正確做法是先用檢索縮小範圍，只取出相關的 10–20 份文件（約 1,500–30,000 tokens），再視需要壓縮**，而非對全庫壓縮。

</details>

---

**題 2（比較）：** 一個旅遊助理系統需要回答各種問題（訂位查詢、政策諮詢、行程建議），文件庫有 500 份文件，每份 2,000–5,000 tokens，LLM 的 context window 是 4,096 tokens。請比較「只用抽取式摘要壓縮」和「RAPTOR + LongLLMLingua 二階段」兩種策略，分析各自的例外條件保留率風險與建索引成本。

<details><summary>解答</summary>

**只用抽取式摘要壓縮：**
- 建索引成本：低（離線計算每句重要性分數，不需要 LLM）
- 例外條件保留率風險：高。重要性評分以頻率或 TF-IDF 為基礎，低頻但關鍵的例外條件（如「21:00 截止」）容易被排到低分而丟棄。
- 問題類型多樣時，無法同時對「訂位查詢」和「政策諮詢」都最佳化選句策略。

**RAPTOR + LongLLMLingua 二階段：**
1. RAPTOR 對 500 份文件建多層索引，取得最相關的 10 個段落（約 2,000 tokens）
2. LongLLMLingua 把 2,000 tokens 壓縮到 1,500 tokens，針對具體問題保留關鍵例外條件
3. 連同問題送入 LLM（1,500 + 500 tokens prompt ≈ 2,000 tokens，在 4,096 以內）

- 建索引成本：高（RAPTOR 需對 500 份文件多次呼叫 LLM）
- 例外條件保留率：在第二步 LongLLMLingua 針對問題壓縮，保留率顯著高於純抽取式
- 主要風險：RAPTOR 聚類錯誤時，第一步就沒取到相關段落，後續無法補救

**結論：** 問題類型多樣、文件庫固定時，二階段策略在例外條件保留率上明顯佔優，代價是更高的建索引成本與架構複雜度。

</details>
