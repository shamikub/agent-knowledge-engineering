# 5.1 一筆評估案例有哪些部分

## 學習目標

完成本節後，你能夠：

1. 描述一筆評估案例（evaluation case）的四個組成部分，並說明每個部分的用途。
2. 解釋為何訂位信改寫後不能同時進入訓練集和測試集，以及如何設計切分規則避免資訊洩漏（distribution leak）。
3. 設計按失敗模式分片（slice）的評估報告，讓不同問題類型的系統表現一目了然。

**先備知識**：讀過 Chapter 4 RAG 架構（4.5 節）；知道什麼是查詢、候選文件與答案。

---

## 1. 為什麼評估資料集這麼難設計？

RAG 系統的輸出是自然語言，不像分類器只有對錯兩種。同一個問題，「可以取消」和「免費取消截止日前可以取消，之後收費 50%」都可能算正確，但第二個回答更有用。再加上：

- 同一則訂位確認信有多份改寫（換格式、換旅館名稱），如果不小心把兩個版本分到訓練集和測試集，系統只要記住語言模式就能答對，根本沒測到泛化能力。
- 標注者對「正確答案」的判斷可能分歧，沒有衝突解決流程，資料就會有雜訊。
- 一個問題的正確答案可能需要不只一份文件，只記錄一份會讓評估工具把等價的組合算錯。

本節系統性地解決這三個問題。

---

## 2. 一筆評估案例的四個組成部分

每一筆評估案例（以下簡稱「案例」）包含：

| 欄位 | 英文對照 | 說明 |
|---|---|---|
| 輸入查詢 | input query | 使用者提出的問題，或一段描述場景的文字 |
| 完整證據集合 | complete evidence set | 足以回答這筆查詢的所有相關文件（可能多份） |
| 預期處置 | expected action | 系統應採取的行動或應輸出的答案類型 |
| 可接受引用 | acceptable citations | 允許被引用的來源清單（含等價替代組合） |

### 2.1 輸入查詢

輸入查詢應還原使用者在對話時的實際措辭，不加整理。若同一問題有多種說法（例如「我可以退訂嗎」與「取消訂房有沒有手續費」），每種措辭都算獨立案例，或在欄位中記錄「語義等價查詢」（paraphrase）清單。

### 2.2 完整證據集合

這是最容易被省略的欄位。完整證據集合不只記錄「答案在哪一份文件」，而是記錄「哪些文件的哪些段落，組合起來才足以回答問題」。

範例：「現在取消訂房會不會被收費？」需要：

- 訂位確認信（含訂位日期、入住日期）
- 取消政策文件（含收費門檻與計算方式）

如果只記錄取消政策，系統拿不到訂位日期就無法判斷是否在免費期內。

### 2.3 預期處置

預期處置描述系統應該「做什麼」，而不只是「說什麼」。例如：

- **應答型**：直接回答問題，並引用來源。
- **澄清型**：詢問缺少的資訊（如訂位姓名）後再答。
- **拒答型**（abstain）：說明目前資訊不足以回答，並說明缺少哪些資訊。

拒答型預期處置同樣需要標注，而且要記錄「不能回答的原因」（例如：知識庫中沒有該旅館的取消政策）。

### 2.4 可接受引用

同一個正確答案可能來自多個等價的來源組合：

- 訂房確認信（含完整入住資訊）+ 取消政策 PDF
- 一封涵蓋訂房與條款的整合確認信

兩種來源組合都應標注為可接受，不然系統找到等價的第二種組合就會被評分工具算錯。

## 3. 完整算例：以訂位確認信設計一筆案例

### 情境

A 和 B 訂了巴黎某旅館，訂位確認信如下（簡化版）：

```
訂單編號：RES-2026-0847
入住：2026-12-20（週日）
退房：2026-12-23（週三）
旅館：Hotel du Nord, Paris
免費取消截止：2026-12-17 23:59（巴黎時間）
逾期取消：收取首晚房費 EUR 189
```

### 步驟一：填寫輸入查詢

```
今天是 12 月 16 日，我想取消 RES-2026-0847，會被收費嗎？
```

### 步驟二：填寫完整證據集合

| 文件 ID | 段落 | 關聯 |
|---|---|---|
| DOC-RES-0847 | 免費取消截止：2026-12-17 23:59 | 判斷截止日 |
| DOC-RES-0847 | 逾期取消：收取首晚房費 EUR 189 | 收費金額 |
| DOC-POLICY-NDR-2026 | 取消費用計算方式（同一條款） | 備用來源 |

注意：若系統只找到 DOC-POLICY-NDR-2026 而沒有 DOC-RES-0847，仍無法確認「這筆訂位的截止日是幾號」（因為同一旅館的不同房型可能有不同截止規則）。

### 步驟三：填寫預期處置

```
應答型。
正確回答：12 月 16 日仍在免費取消期內（截止日 12 月 17 日），
          可以免費取消，不收費。
需引用：訂位確認信中的截止日。
```

### 步驟四：填寫可接受引用

```
選項 A：DOC-RES-0847（訂位確認信，含截止日）
選項 B：DOC-POLICY-NDR-2026（如果政策文件明確記載同一截止日）
兩者任一即可；若引用選項 B，仍需同時引用 DOC-RES-0847 確認訂單號。
```

### 潛在陷阱整理

| 陷阱 | 說明 |
|---|---|
| 只記錄一份文件 | 遺漏另一份也能回答問題的等價文件，造成假陰性 |
| 未記錄拒答條件 | 訂位姓名不對時應拒答，但案例沒有記錄此分支 |
| 答案包含舊版條款 | 若知識庫同時有 2025 與 2026 版政策，要指定以哪版為準 |
| 預期處置過於寬鬆 | 只寫「回答有關取消的問題」而不列具體金額，無法自動評分 |

## 4. 資料切分策略：按 case 切，不按句子切

### 核心原則

切分單位是**整筆案例（case）**，不是段落或句子。原因如下：

同一筆訂位確認信，把第一段放訓練、第二段放測試，兩個切片在語言模式上高度相關。模型看過第一段後，遇到第二段幾乎等於已見過這張訂單。

### 反例：同一訂位的兩次改寫

原始版：
```
RES-2026-0847 · Hotel du Nord · 免費取消截止 2026-12-17
```

改寫版（換格式）：
```
確認單號 0847-2026 · 北都旅舍巴黎 · cancellation no-fee deadline: Dec 17 2026
```

若原始版在訓練集、改寫版在測試集，系統看到「0847」就已經記住答案。**這兩個版本只能進同一個切分（都在訓練或都在測試），絕不能分開。**

### 切分規則

1. 以**訂位 ID**（booking reference）作為分組鍵（group key）。
2. 同一訂位的所有改寫版本必須在同一組。
3. 切分時按組為單位做 train / validation / test 分割。
4. 若使用 k-fold，fold 邊界同樣在組的層級，不在案例的層級。

## 5. 四個切片的分片報告設計

在整體指標外，額外按以下四個「失敗模式切片（failure slice）」分別報告：

| 切片名稱 | 定義 | 設計目的 |
|---|---|---|
| 跨日夜車（overnight）| 訂位涉及夜車跨日，日期計算容易出錯 | 測試時間推理能力 |
| 版本衝突（version conflict）| 知識庫同時含舊版與新版政策文件 | 測試版本過濾能力 |
| 缺資料（missing data）| 至少一份必要文件不在知識庫 | 測試拒答準確率 |
| 別名（alias）| 旅館或地名有多種寫法 | 測試匹配寬容度 |

報告模板：

```
切片            | 樣本量 | 整體正確率 | 拒答率 | 誤放行率
----------------|--------|-----------|--------|--------
全體            |   100  |   72%     |  18%   |  10%
跨日夜車        |    15  |   53%     |  27%   |  20%
版本衝突        |    20  |   60%     |  10%   |  30%
缺資料          |    18  |   —       |  83%   |  17%
別名            |    12  |   75%     |  17%   |   8%
```

注意：「缺資料」切片的「整體正確率」欄位留空，因為預期處置是拒答，正確答案不是回答而是說明資訊不足。

## 6. 標注流程

### 6.1 多標注者一致性（inter-annotator agreement）

每筆案例由至少兩位標注者獨立完成後，計算一致性指標：

- **Cohen's kappa**：常用於預期處置（應答 / 澄清 / 拒答）的分類一致性。
- **Jaccard 相似度**：用於可接受引用集合的重疊程度。

一致性低的案例進入仲裁（adjudication）流程。

### 6.2 仲裁（adjudication）

| 情形 | 處理方式 |
|---|---|
| 兩人對預期處置意見不同 | 第三位標注者裁定，或邀請領域專家決定 |
| 一人認為可引用 A，另一人認為要引用 A+B | 保守標注：採較嚴格要求（A+B）並記錄分歧 |
| 兩人都不確定 | 標記為 `unknown`，不猜測，不進評估計算 |

### 6.3 標記 unknown 而非猜測

如果標注者對正確答案不確定（例如：政策文件措辭曖昧，法律意義不明），應標記 `unknown` 並記錄不確定原因，而不是猜一個答案。

`unknown` 案例在評估時排除計算，但保留在資料庫中，以便日後補強知識庫後重新標注。

## 7. 習題

**習題 1（機制）**：一筆案例的「完整證據集合」和「可接受引用」有什麼不同？為何需要兩個欄位？

<details><summary>解答</summary>

「完整證據集合」是回答這個問題所需的所有相關文件，確保評估時不會因為系統找到等價文件而被算錯。「可接受引用」是在最終答案中允許引用的來源清單，可以是多個等價選項。

需要兩個欄位，因為「需要哪些文件才能回答」和「哪些文件可以作為引用出處」是不同問題。例如，系統可能需要訂位信和政策文件來推理，但答案只需引用政策文件；若把兩個欄位混用，就會錯誤要求所有推理來源都出現在引用中。
</details>

---

**習題 2（除錯）**：某評估報告顯示，測試集的正確率比訓練集高出 15%。這現象正常嗎？可能的原因是什麼？

<details><summary>解答</summary>

這現象不正常，通常訓練集表現應高於或接近測試集。可能原因包括：

1. **分布洩漏**：同一訂位的改寫版本分別進了訓練和測試集，測試集中有「訓練集的近親」，系統靠記憶作答。
2. **測試集較容易**：切分時沒有控制難度分布，測試集恰好缺少困難的「缺資料」或「版本衝突」案例。
3. **評估指標不一致**：訓練集和測試集採用不同的評估標準或不同的標注者。

診斷方法：檢查訓練集和測試集中各切片的樣本比例是否相近；用 booking reference 作為分組鍵重新切分。
</details>

---

**習題 3（選型）**：你正在設計一個有 500 筆案例的評估資料集，其中 50 筆涉及夜車跨日。你有兩個切分方案：(A) 完全隨機切分 70/15/15；(B) 按 booking reference 分組後，在組內做 stratified split，確保每個切片在各分割中的比例相近。哪個方案較好？為什麼？

<details><summary>解答</summary>

方案 B 較好，原因有二：

1. **防止洩漏**：隨機切分（方案 A）不保證同一訂位的改寫版本在同一組，可能造成分布洩漏。按 booking reference 分組確保同一訂位的所有版本進同一切分。

2. **保持切片比例**：Stratified split 確保「夜車跨日」等難度較高的案例在訓練、驗證、測試集中各佔相近比例，讓評估指標在各切片上都具統計意義。方案 A 的隨機性可能讓 50 筆夜車案例集中在某一切分，使該切片的指標不穩定。
</details>
