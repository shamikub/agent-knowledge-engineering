# 5.2 四次重跑定位錯因

## 學習目標

完成本節後，你能夠：

1. 描述 Oracle Retrieval（人工選定證據）的設計邏輯，以及它如何把「檢索問題」和「推理問題」分離。
2. 設計對照實驗，逐步縮小錯誤來源的範圍，而不是同時改動多個模組。
3. 解釋位置偏差（position bias）的成因，以及如何用對調實驗驗證它是否影響系統表現。

**先備知識**：讀過 5.1 節（案例結構），知道 RAG 的三個主要模組：檢索器（retriever）、重排器（reranker）、答案生成器（generator）。

---

## 1. 問題定義：RAG 答錯了，錯在哪裡？

當 RAG 系統對一筆案例給出錯誤答案，可能的原因分布在三個層級：

| 層級 | 可能問題 | 表徵 |
|---|---|---|
| 檢索層 | 正確文件沒進候選集；正確文件排名太低；版本過濾失效 | 答案中引用的文件不支持結論，或引用的是過期版本 |
| 推理層 | 正確文件都在，但生成器算錯日期、忽略例外條款、混淆條件 | Oracle Retrieval 後仍然答錯 |
| 資料層 | 知識庫根本沒有這筆訂位的相關文件 | 任何設定下都應拒答，但系統卻瞎猜 |

如果不系統性地隔離每個層級，改了一個參數後表現提升，你仍然不知道**為什麼**提升，下次遇到類似問題時無從下手。

## 2. 四次重跑的設計邏輯

每次重跑只改動一個變數，其餘固定不動。

### 第 0 跑：基線（end-to-end baseline）

完整執行系統，不做任何人工介入。記錄每筆案例的：
- 實際檢索到的文件清單（含排名）
- 生成的答案
- 自動評分結果

這是所有後續對照的起點。

### 第 1 跑：Oracle Retrieval

把實際檢索器的輸出替換成「人工選定的正確證據」（即 5.1 節定義的完整證據集合），其餘（重排、生成器、提示模板）一律不動。

**診斷邏輯**：

```
若第 1 跑表現顯著優於第 0 跑
  → 問題在檢索層（正確文件沒進來，或排名太低）
  → 下一步：分析候選召回率、重排器輸出、版本過濾規則

若第 1 跑表現與第 0 跑相近（仍然答錯）
  → 問題在推理層（生成器拿到正確文件也答不對）
  → 下一步：分析條件表示、時間計算、必填欄位是否缺失
```

### 第 2 跑：加入舊版文件、調換證據位置

在第 1 跑（Oracle 證據）的基礎上，分別進行兩個干擾實驗：

**實驗 2A：加入舊版文件**
在已選定的正確証據外，額外插入一份過期的舊版政策文件。若系統表現下降，說明生成器無法正確過濾版本，或提示模板沒有引導模型優先使用較新的資料。

**實驗 2B：調換證據位置**
把正確文件從第一個位置移到最後一個位置（其餘不變）。若表現下降，說明系統存在位置偏差（position bias）。

### 第 3 跑：只看特定切片

以 5.1 節定義的四個切片（跨日夜車、版本衝突、缺資料、別名）各自重跑，對照切片間的錯誤率差異，確認哪種失敗模式最嚴重。

## 3. 完整算例：取消政策版本衝突

### 情境

知識庫中同時存在兩份政策文件：

```
DOC-POLICY-2025（舊版）：逾期取消收取首晚房費的 50%
DOC-POLICY-2026（新版）：逾期取消收取首晚房費的全額（100%）
```

案例查詢：
```
我的訂單 RES-2026-0847 入住日是 12 月 20 日，今天是 12 月 18 日，
免費截止是 12 月 17 日。現在取消要付多少錢？
```

預期處置：引用 2026 版政策，回答「需支付首晚全額房費 EUR 189」。

### 第 0 跑（基線）結果

```
檢索器返回：
  1. DOC-POLICY-2025（相關性分數 0.82）
  2. DOC-POLICY-2026（相關性分數 0.79）
  3. DOC-RES-0847（相關性分數 0.71）

生成器回答：
  「逾期取消將收取首晚房費的 50%，約 EUR 94.5。」

評分：錯誤（金額錯誤，引用舊版）
```

基線答錯，但現在不知道是因為檢索器排名問題（舊版排第一），還是生成器即使看到新版也會選舊版。

### 第 1 跑（Oracle Retrieval）結果

把檢索結果替換為：

```
1. DOC-POLICY-2026（新版）
2. DOC-RES-0847
```

```
生成器回答：
  「逾期取消將收取首晚全額房費 EUR 189。」

評分：正確
```

**診斷**：Oracle 後正確 → 問題在檢索層。生成器拿到正確文件可以答對，不需要改生成器或提示模板。下一步去查為什麼 DOC-POLICY-2025 排第一。

### 第 2A 跑（Oracle + 舊版干擾）

把檢索結果改為：

```
1. DOC-POLICY-2025（舊版，插入在最前面）
2. DOC-POLICY-2026（新版）
3. DOC-RES-0847
```

```
生成器回答：
  「逾期取消將收取首晚房費的 50%，約 EUR 94.5。」

評分：錯誤
```

**診斷**：舊版文件出現在第一位時，生成器又回到錯誤答案。這說明有位置偏差，且生成器沒有版本過濾邏輯（無法自動識別 2025 版已被 2026 版取代）。

### 第 2B 跑（Oracle + 位置對調）

把 DOC-POLICY-2026 移到最後：

```
1. DOC-RES-0847
2. DOC-POLICY-2025（舊版）
3. DOC-POLICY-2026（新版，移到最後）
```

```
生成器回答：
  「逾期取消將收取首晚房費的 50%，約 EUR 94.5。」

評分：錯誤
```

**診斷**：即使只有 2026 版在第三位（沒有特別說它是「舊版」），生成器仍傾向使用前面出現的文件。這確認了位置偏差的存在。

### 診斷報告

```
case_id:        RES-2026-0847-cancel
切片:           版本衝突（version conflict）
基線結果:       錯誤（使用 2025 版，金額 EUR 94.5）
Oracle 結果:    正確（使用 2026 版，金額 EUR 189）
錯誤層:         檢索層（排名）+ 生成器位置偏差
改進建議:
  1. 在 reranker 加入文件日期特徵，讓較新版本獲得加分。
  2. 在提示模板加入「優先使用最新版本政策文件」的指引。
  3. 在知識庫加入版本失效標記（deprecated flag），讓舊版文件在候選生成時降權。
```

## 4. 位置偏差（position bias）與 Lost in the Middle 效應

研究發現（Liu et al., 2023 "Lost in the Middle"），語言模型在回答多文件問題時，傾向使用出現在輸入**最前面**或**最後面**的文件，對中間位置的文件關注度較低。這稱為「位置偏差（position bias）」。

**驗證實驗設計**：

取同一批 Oracle 案例（已知正確文件），做以下三組：

| 組別 | 正確文件位置 | 其他文件 |
|---|---|---|
| 組 A | 第 1 位（最前） | 無關文件填滿後面位置 |
| 組 B | 中間（如第 3 位，共 5 份） | 無關文件填前後 |
| 組 C | 最後 1 位 | 無關文件填滿前面位置 |

若組 B 的正確率顯著低於組 A 和組 C，說明系統有 Lost in the Middle 問題。

**緩解方法**：

1. 在提示中明確要求模型「逐一審視每份文件再作答」。
2. 在候選列表中多次重排，以不同順序送入後取多數決（ensemble）。
3. 若使用工具呼叫（tool call）架構，讓模型主動選擇要讀哪份文件，而非被動接受排序。

## 5. 反例：同時改動兩個模組

下面是一個常見的錯誤做法：

```
週一：測試基線 → 正確率 68%
週二：同時 (1) 更新 reranker 模型 (2) 改寫答案生成的提示模板
週三：再次測試 → 正確率 76%
```

問題：正確率提升了 8%，但你不知道是 reranker 的貢獻、提示模板的貢獻，還是兩者交互作用。如果下次效果變差，你也不知道要回滾哪個。

**正確做法**：每次只改一個變數，其餘固定。如果時間緊迫、必須同時部署，至少在 A/B 測試中設計四組：原始（無改動）、只改 reranker、只改提示、兩者都改。

## 6. 習題

**習題 1（機制）**：Oracle Retrieval 實驗中，生成器輸出在 Oracle 前後表現一樣差。這代表什麼？下一步應該怎麼做？

<details><summary>解答</summary>

代表問題不在檢索層，而在推理層（生成器）。即使給了正確的文件，生成器仍然無法得出正確答案。

下一步診斷方向：
1. **條件表示**：正確文件中是否有生成器難以解析的格式（例如複雜表格、巢狀條件）？
2. **時間計算**：問題是否需要日期運算（例如「今天距截止日還有幾天」）？可以嘗試把時間計算外包給確定性程式（code execution）。
3. **必填欄位**：生成器是否因為某個欄位（如訂位姓名）不在文件中就瞎猜？可以檢查答案是否包含「捏造」（hallucination）的資訊。
4. **否定條件**：問題是否含有例外條款（例如「以下情形除外」）？可以設計專門的否定條件測試集驗證。
</details>

**習題 2（手算）**：某系統在以下四次重跑中得到這些正確率：

| 跑次 | 設定 | 正確率 |
|---|---|---|
| 第 0 跑 | 基線 | 55% |
| 第 1 跑 | Oracle Retrieval | 85% |
| 第 2A 跑 | Oracle + 舊版文件插入第 1 位 | 60% |
| 第 2B 跑 | Oracle + 正確文件移至最後 | 70% |

根據這四個數字，分別指出：(a) 有多大比例的錯誤可歸因於檢索層？(b) 位置偏差的影響有多大？(c) 舊版干擾的額外影響有多大？

<details><summary>解答</summary>

以百分點為單位，基準是 Oracle 正確率 85%：

(a) **檢索層貢獻**：基線 55% → Oracle 85%，差距 30 個百分點。在原始 45% 錯誤中，約 30/45 ≈ 67% 可歸因於檢索層問題。

(b) **位置偏差影響**：Oracle（正確文件在第 1 位）85% → 正確文件移至最後 70%，差距 15 個百分點。這 15 個百分點的損失來自位置偏差。

(c) **舊版干擾的額外影響**：Oracle + 舊版插入第 1 位 60% 與 Oracle + 位置對調 70% 相比，多損失 10 個百分點。這部分來自生成器無法區分舊版與新版（版本過濾失效），超過純位置偏差（15pp）以外的額外損失。

注意：這些估計假設效應可加，實際上可能存在交互作用，解讀時需謹慎。
</details>

---

**習題 3（選型）**：你發現 Oracle Retrieval 後系統表現從 60% 升到 90%，但你的老闆說「直接改提示模板，不用管檢索器」。這個建議合理嗎？如何用數據反駁？

<details><summary>解答</summary>

不合理。Oracle 後表現升到 90%，代表檢索層是主要瓶頸：30 個百分點的差距中，有高達 90%−60%＝30pp 可由改善檢索來回收，但提示模板只影響推理層，對已確認的檢索問題沒有幫助。

反駁方式：
1. 展示診斷報告：列出具體的錯誤案例，說明「正確文件根本沒進候選集」（例如候選集 top-10 中沒有 DOC-POLICY-2026）。如果正確文件不在候選集，提示模板再好也看不到這份文件。
2. 做一個反向對照：固定最好的提示模板，不改檢索器，預期正確率仍停留在 60% 左右。這直接顯示提示模板無法解決檢索問題。
3. 成本分析：改善檢索器（例如加入版本過濾）的工程成本可能低於反覆調整提示模板，且效果更可預測。
</details>
