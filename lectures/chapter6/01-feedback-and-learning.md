## 1. 情境設定：同一件錯誤，三種診斷

**故事背景：** 旅客 A 與旅客 B 一起預訂了布拉格的旅館（2 月 14 日 Check-in）。B 因故改航班，改為 2 月 15 日才抵達；A 照常依原計畫入住。訂房確認信的原始措辭是「二位旅客同住」，系統判斷「B 晚到 → 整筆訂房取消」，觸發了取消流程，害 A 當晚無房可住。

人工客服事後改判：「A 照常入住，僅 B 的 Check-in 時間後移，訂房不取消。」

這一筆改判，能觸發哪些層次的更新？

## 2. 三種更新層次

```
┌─────────────────────────────────────────────────────────────┐
│                       AI Agent 系統                          │
│                                                             │
│  ① 知識層   ── 存的是「事實」（誰訂了什麼）                    │
│  ② 策略層   ── 存的是「規則」（什麼時候該做什麼）               │
│  ③ 權重層   ── 存的是「模式」（模型參數）                      │
└─────────────────────────────────────────────────────────────┘
```

| 層次 | 修正什麼 | 適用情境 | 成本 |
|------|---------|---------|------|
| 知識修正 | 一筆或一批事實錯誤 | 資料缺漏、來源不完整 | 低（改資料庫） |
| 策略更新 | 決策邏輯、前置條件 | 規則本身有漏洞 | 中（改程式碼或提示） |
| 權重更新 | 模型的內化偏見或泛化能力 | 大量同類錯誤、跨任務遷移 | 高（需重新訓練） |

---

## 3. 知識修正：更新版本與來源

### 3.1 什麼情況走這條路

當錯誤是因為「資料本身有問題」：漏了某筆資訊、來源說錯了、版本過期。
策略和模型都沒有問題，只是拿到的輸入是錯的。

### 3.2 Bitemporal 更新（複習第三章）

每筆知識記錄兩個時間：

- **有效時間（valid time）**：事實在現實世界成立的期間
- **交易時間（transaction time）**：這筆記錄被系統寫入的時間

改判案例的更新操作：

```text
原始紀錄（交易時間 T1 寫入）：
  booking_id  : BRG-2024-0214
  valid_time  : [2024-02-14, 2024-02-16)
  guests      : ["A", "B"]
  status      : CONFIRMED
  note        : "兩位旅客同住，B 若未到視為整筆取消"   ← 這行有問題

更新後（交易時間 T2 寫入，T1 的紀錄保留不刪）：
  booking_id  : BRG-2024-0214
  valid_time  : [2024-02-14, 2024-02-16)
  guests      : {"A": {"checkin": "2024-02-14"}, "B": {"checkin": "2024-02-15"}}
  status      : CONFIRMED
  note        : "A 照常入住；B 後一日 Check-in，各自計算"
  source_ref  : ["booking-email-v2.pdf", "cs-override-20240214-001"]
```

**重點：** 舊版本不刪，只是在交易時間軸上關閉。之後若要重播 2024-02-14 當時的決策，仍能找到當時看到的知識版本。

### 3.3 反例：只更新知識但策略有 bug

假設策略邏輯是：
```python
if any(guest.checkin != booking.checkin_date for guest in booking.guests):
    cancel_entire_booking()   # ← bug：只要有人晚到就整筆取消
```

即使把 B 的 Check-in 時間更新到資料庫，策略仍然會觸發取消。**知識更新後問題仍在**，說明根本原因在策略層，而不是知識層。

## 4. 策略更新：修正決策邏輯

### 4.1 什麼情況走這條路

知識是對的，但「處理邏輯」有漏洞：前置條件判斷錯誤、執行順序有問題、沒有考慮邊界情況。

### 4.2 策略修正範例

將上述 bug 修正後的策略：

```python
def handle_late_checkin(booking, guest_id, new_checkin_date):
    """
    個別旅客改 Check-in 日期，不影響整筆訂房。
    前置條件：
      1. booking.status == CONFIRMED
      2. new_checkin_date 在 booking.checkout_date 之前
      3. 至少一位旅客維持原 Check-in 日期，或旅館允許空房過渡
    """
    guest = booking.get_guest(guest_id)
    assert booking.status == "CONFIRMED"
    assert new_checkin_date < booking.checkout_date
    guest.checkin = new_checkin_date
    booking.save_with_audit(actor="system", reason="guest_late_arrival")
    # 整筆訂房狀態維持 CONFIRMED，不觸發取消
```

策略更新通常對應到：
- 修改提示（prompt）中的指令或範例
- 修改 agent 的 tool 呼叫前置條件檢查
- 修改 policy engine（如 OPA）的規則

## 5. 權重更新與 DAgger

### 5.1 什麼是 Covariate Shift

行為複製（Behavior Cloning）有一個根本問題：訓練資料是「專家在 *自己的* 狀態分布」下的示範。模型一旦走出訓練分布（犯了一個小錯），後續遭遇的狀態是訓練時從未見過的，錯誤會複合放大。

```
訓練時：  s₀ → s₁ → s₂ → ...    （專家走的路徑）
推論時：  s₀ → s₁' → s₂'' → ...  （模型走的路徑，稍微偏了就越走越偏）
```

### 5.2 DAgger 演算法

DAgger（Dataset Aggregation，Ross et al., 2011）的核心思路：

```
演算法 DAgger
─────────────────────────────────────────
輸入：初始策略 π₁（可以是行為複製的結果）
輸出：混合策略 π̂

for i = 1, 2, ..., N:
  1. 用目前策略 πᵢ 在環境中執行，蒐集軌跡
     → 得到「πᵢ 實際到達的狀態集合」Dᵢ
  2. 對 Dᵢ 中的每個狀態，請專家（人工）標注正確動作
     → 得到新示範 Dᵢ' = {(s, aᵉˣᵖᵉʳᵗ) | s ∈ Dᵢ}
  3. 聚合資料：D = D ∪ Dᵢ'
  4. 在 D 上訓練新策略 πᵢ₊₁
─────────────────────────────────────────
```

**關鍵洞察：** 每一輪蒐集的都是「當前策略會遇到的狀態」，而不是「專家才會到達的狀態」。隨著迭代，策略逐漸修正偏差，資料集也逐漸覆蓋策略實際走到的分布。

### 5.3 DAgger 在改航班情境的具體算例

**初始狀況：** 策略 π₁ 是靠行為複製訓練的，在正常案例表現良好，但一旦遇到「某位旅客改票後又問要不要改晚餐」這種「錯誤復原後的後續狀態」就不知道怎麼處理。

**第一輪 DAgger 迭代：**

```
步驟 1：讓 π₁ 實際執行
  狀態序列：
    s₀: {旅客B改航班, 晚餐訂位=CONFIRMED, 助理判斷=整筆取消}  ← 策略犯錯
    s₁: {booking_status=CANCELLED（錯誤）, A 傳訊息詢問晚餐}
    s₂: {系統不知道怎麼回應 s₁，因為訓練資料沒有這種後續狀態}

步驟 2：人工標注 s₁ 的正確處理
  s₁ 的正確動作：
    - 先查原始訂位（booking_id: DIN-0214-A）
    - 確認 A 仍有效（A 的入住未受影響）
    - 恢復晚餐訂位，備註「B 缺席，調整為 1 人份」
    - 回覆 A：「您的晚餐訂位已確認，已調整為 1 人份」

步驟 3：聚合進訓練集
  D = D_original ∪ {(s₁, 恢復訂位+回覆A)}

步驟 4：訓練 π₂，現在 π₂ 看到「取消後收到詢問」時知道先查再恢復
```

**第二輪 DAgger 迭代（之後）：**
- π₂ 的錯誤變少，蒐集到的 Dᵢ 越來越接近正確路徑
- 專家標注量逐漸減少

**注意事項：** DAgger 有標注成本，每輪需要人工介入。真實系統通常只跑幾輪，或用「有限預算的 DAgger」。

## 6. 權重更新與 Continual Learning

### 6.1 Catastrophic Forgetting

神經網路在學習新任務時，舊任務的能力會退化，稱為災難性遺忘（catastrophic forgetting）。這是因為梯度更新會覆蓋掉對舊任務重要的參數。

**量化範例（來自旅行助理系統的假設數據）：**

```
新任務：學習「改航班後晚到」的處理
舊任務：「住宿訂位查詢」的處理

更新前：
  改航班正確率：62%
  住宿查詢正確率：89%

只用新任務資料訓練後：
  改航班正確率：+8% → 70%
  住宿查詢正確率：-12% → 77%   ← 遺忘！
```

住宿查詢下降 12 個百分點，代表模型「忘記」了舊有能力。

### 6.2 Replay Buffer 機制

Replay buffer 保存舊任務的樣本，在新任務訓練時混入，讓模型同時看到新舊任務的示範。

```
Replay Buffer 更新流程
────────────────────────────────────
Buffer B 保存過去 K 個任務各 M 個樣本

當訓練新任務 T_new 時：
  1. 從 B 中取出代表性舊樣本 B_sample
  2. 合併訓練集：D_train = D_new ∪ B_sample
  3. 在 D_train 上更新參數
  4. 將部分 T_new 的樣本加入 B（替換最舊的）

每輪驗證：
  - 新任務指標（改航班正確率）必須 ≥ 目標值
  - 舊任務指標（住宿查詢正確率）不得下降超過閾值（例如 3%）
────────────────────────────────────
```

**使用 Replay Buffer 後的結果（同樣場景）：**

```
更新前：
  改航班正確率：62%
  住宿查詢正確率：89%

Replay（混入 20% 舊樣本）後：
  改航班正確率：+6% → 68%   ← 稍微少一點提升
  住宿查詢正確率：-2% → 87% ← 遺忘被大幅緩解
```

代價是新任務提升幅度略小（+6% vs +8%），但這是可接受的取捨。

### 6.3 設定發版門檻

```python
RELEASE_THRESHOLDS = {
    "flight_change_accuracy":  0.68,   # 新任務目標
    "hotel_query_accuracy":    0.86,   # 舊任務不能低於此值
    "dinner_booking_accuracy": 0.84,   # 其他舊任務
}

def check_release(eval_results: dict) -> bool:
    for task, threshold in RELEASE_THRESHOLDS.items():
        if eval_results[task] < threshold:
            print(f"[BLOCK] {task}: {eval_results[task]:.2%} < {threshold:.2%}")
            return False
    return True
```

## 7. 完整算例：同一件「改航班」案件的三條路徑

**輸入案件：**
```
案件 ID   : CS-2024-0214-003
描述      : 旅客 B 改航班晚到，助理錯誤取消整筆訂房
人工改判  : A 照常入住，B 後一日 Check-in，訂房不取消
```

**路徑一：知識修正**
```
確認錯因：知識庫缺少「各旅客可分開 Check-in」的資訊

修正動作：
  1. 在知識庫新增規則（有效時間自 2024-02-14 起）：
     "多人訂房：每位旅客 Check-in 時間獨立計算，
      一人改期不影響他人及整筆訂房狀態。"
  2. 關閉原有衝突規則的有效時間（valid_until = 2024-02-14）
  3. 在來源欄記錄：source_ref = ["CS-override-003", "booking-policy-v2"]

驗證方式：
  重播案件，策略拿到新知識後，應不再觸發取消
```

**路徑二：策略更新**
```
確認錯因：策略邏輯「任何旅客 Check-in 晚到 → 取消整筆」

修正動作：
  1. 修改提示或工具前置條件：
     "改 Check-in 日期前，先確認是否為多人訂房。
      若為多人，僅更新該旅客的 Check-in，不影響整筆。"
  2. 加入新測試案例：
     input:  B 改 Check-in，A 不變
     expect: booking.status 仍為 CONFIRMED
     forbid: cancel_booking() 被呼叫

驗證方式：
  新策略跑過原案件，確認不再呼叫取消工具
```

**路徑三：權重更新**
```
確認錯因：模型在「改票後後續詢問」的狀態分布上泛化不足

修正動作（DAgger 一輪）：
  1. 讓現有策略跑五個類似改票案件
  2. 標注每個案件中「犯錯後的後續狀態」的正確動作
  3. 混入舊任務 replay 樣本，訓練新版本
  4. 跑回歸：改票 +6%，住宿查詢 -2%（在門檻內）

驗證方式：
  評估集中「改票後續」切片的正確率達到 ≥ 70%
```

## 8. 方法比較：三種更新層的選型指引

| 面向 | 知識修正 | 策略更新 | 權重更新 |
|------|---------|---------|---------|
| **修正目標** | 事實錯誤、來源缺漏 | 邏輯漏洞、邊界條件 | 泛化偏差、跨任務遷移 |
| **所需條件** | 找到正確的事實來源 | 能描述正確的規則 | 足夠的示範或回饋樣本 |
| **成本** | 低（改資料庫） | 中（改程式或提示） | 高（訓練基礎設施） |
| **生效速度** | 立即 | 次日部署後 | 需要訓練週期 |
| **風險** | 新事實可能矛盾舊有 | 規則改錯可能引入新 bug | Catastrophic forgetting |
| **可回滾性** | 高（bitemporal 保留舊版） | 中（需程式碼版本控制） | 低（需保存 checkpoint） |
| **適用場景** | 一次性事件、政策更新 | 系統性邏輯錯誤 | 大量同類錯誤、新類型任務 |

**選型決策樹：**

```
錯誤來自「資料是錯的」？
  → 是：知識修正

錯誤來自「規則有漏洞」（即使資料正確，決策仍錯）？
  → 是：策略更新

錯誤是「在某類狀態下系統性犯錯，且無法用規則描述」？
  → 是：權重更新（DAgger / Continual Learning）
```

## 9. 習題

**習題 1（機制）**
旅客 A 在 Check-in 後傳訊息：「我的早餐套餐為什麼不見了？」系統查詢後回答「您沒有訂早餐」，但人工查詢後發現是訂房確認信中明確包含早餐。

請問這個錯誤最可能是哪個層次的問題？說明你的判斷依據。

<details><summary>解答</summary>

這是**知識層**的問題。

**判斷依據：**
1. 訂房確認信中明確包含早餐，代表「事實」是正確的，只是系統的知識庫沒有把早餐套餐這個資訊讀入或儲存。
2. 策略邏輯（查詢早餐 → 回傳結果）本身沒有問題，只是查詢到的資料是不完整的。
3. 修正方式：重新解析確認信，把早餐套餐資訊存入知識庫，並更新 transaction time。

如果這個錯誤是「確認信明明有早餐，系統也有記到，但助理回答時忽略了」，才需要考慮策略或權重層。

</details>

**習題 2（手算 DAgger）**
策略 π₁ 在五個測試案例中，有三個案例（s₂、s₄、s₅）走到了訓練資料從未出現的錯誤後續狀態。請說明 DAgger 第一輪迭代後，新的訓練集 D 會新增哪些內容，以及 π₂ 相比 π₁ 在哪個方面應有改善。

<details><summary>解答</summary>

**新增到訓練集 D 的內容：**
- (s₂ 的後續狀態, 專家在 s₂ 之後的正確動作)
- (s₄ 的後續狀態, 專家在 s₄ 之後的正確動作)
- (s₅ 的後續狀態, 專家在 s₅ 之後的正確動作)

共新增三組 (state, expert_action) 配對。

**π₂ 相比 π₁ 的改善：**
1. π₂ 在 s₂、s₄、s₅ 型別的後續狀態上，能做出更接近專家的動作（因為訓練資料現在涵蓋這些狀態）。
2. π₂ 在原本的訓練狀態上應維持相似表現（因為 D = D_original ∪ 新增的三組，舊資料沒有刪除）。
3. DAgger 的理論保證：隨著迭代輪數增加，策略走到的分布與訓練資料的分布之間的差距（covariate shift）會縮小。

</details>

**習題 3（選型）**
系統在過去一個月內，「改 Check-in 日期」這個操作有 15% 的案例被錯誤執行（觸發整筆取消）。工程師檢查後發現，策略邏輯是正確的，知識庫的資料也是完整的，但模型在輸入訊息包含多個旅客姓名時，無法正確辨識「這句話在說 B 改期，不是 A 改期」。

請問應走哪條更新路徑？說明步驟。

<details><summary>解答</summary>

應走**權重更新**路徑（Continual Learning 配合 DAgger）。

**理由：**
- 知識層無誤（資料完整）
- 策略層無誤（邏輯正確）
- 問題是模型的**實體識別（entity resolution）能力不足**：無法在多人情境下正確辨識「這個動作的主語是誰」，這是模型的泛化偏差，無法用規則修補（因為自然語言表達方式太多樣）。

**建議步驟：**
1. 蒐集過去一個月所有 15% 錯誤案例，標注正確的「主語旅客 → 動作」對應。
2. 用 DAgger 或直接微調（LoRA），在這批資料上更新模型。
3. 混入舊任務 replay 樣本（住宿查詢、餐廳訂位等），避免遺忘。
4. 設定發版門檻：「改 Check-in 錯誤率 ≤ 5%」且「其他任務正確率下降 ≤ 2%」。
5. 通過門檻後才部署新版本。

</details>
