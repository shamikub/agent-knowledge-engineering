# 3.4 壓縮的收益與資訊遺失（Compression）

[章節導覽](intro.md) · [上一節](03-bitemporal-modeling.md)

---

## 學習目標

完成本節後，你能夠：

1. 比較抽取式（extractive）和生成式（abstractive）摘要在資訊保留上的差異，並說明各自的失效情境。
2. 說明 RAPTOR 的遞迴聚類邏輯：為什麼它能同時回答廣泛問題和細節問題。
3. 在固定 token 預算下，量化例外條件保留率，並解釋為何保留率比壓縮比更重要。

**先備知識：** 知道 LLM 有 context window（上下文視窗）限制即可。不需要事先了解向量嵌入。

---

## 1. 任務定義

**問題背景：** LLM 的 context window 有長度上限（例如 4096、8192 tokens）。當輸入文件超過限制，需要在送入模型前壓縮內容。

**輸入：** 長文件（政策條款、訂位確認信、旅遊手冊），可能包含關鍵的例外條件（例如「21:00 前入住」）。

**輸出：** 保留關鍵細節的壓縮版本，讓 LLM 能正確回答後續問題。

**核心張力：** 壓縮比越高，省越多 tokens，但遺失關鍵細節的風險也越高。重要的不只是「壓了多少」，而是「保留了哪些關鍵資訊」。

**衡量指標：**
- **壓縮比（compression ratio）：** `1 - (壓縮後 tokens / 原始 tokens)`
- **例外條件保留率（exception retention rate）：** 壓縮後版本中，原文關鍵例外句子的保留比例
- **任務成功率（task success rate）：** 以壓縮後版本為上下文，LLM 回答問題的正確率

## 2. 架構說明：三種壓縮思路

### 2.1 抽取式摘要（Extractive Summarization）

**原理：** 從原文選出最重要的句子，直接拼接成摘要，不改寫文字。

```
原文：
1. 入住截止時間為晚間 21:00。
2. 旅客須提前與旅館聯繫若無法按時抵達。
3. 旅館訂房包含早餐。
4. 健身房開放時間為 06:00–22:00。
5. 取消政策：7天前免費，3天前50%退款。

抽取式摘要（選句 1, 5）：
入住截止時間為晚間 21:00。取消政策：7天前免費，3天前50%退款。
```

**優點：** 句子來自原文，不會引入幻覺（hallucination）。
**缺點：** 選句依賴重要性評分，若「21:00 前入住」被評為低分（例如文件主題是取消政策），這句話可能被丟棄。

### 2.2 RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）

**核心思想：** 把文件分成段落 → 嵌入向量 → 聚類 → 對每個群組生成摘要 → 遞迴對上層摘要再聚類，建立多層索引樹。

```
層級 2（全域摘要）：
  "薩爾斯堡旅遊住宿取消政策及設施說明"

層級 1（主題摘要）：
  群組 A：入住規則（截止 21:00、晚到通知）
  群組 B：取消費率（7天/3天/1天）
  群組 C：設施（早餐、健身房）

層級 0（原始段落）：
  §1 §2 §3 §4 §5 ...
```

**查詢邏輯：**
- 廣泛問題（「這家旅館有什麼政策？」）→ 在層級 1–2 找答案
- 細節問題（「幾點前要入住？」）→ 從層級 1 的群組 A 下鑽到層級 0

**優點：** 同時支援摘要層級與細節層級的查詢。
**缺點：** 建索引成本高（需要多次 LLM 呼叫）；若聚類把例外條件（如 21:00 截止）歸入錯誤群組，查詢細節時可能找不到。

**論文：** Sarthi et al., "RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval," ICLR 2024. arXiv:2401.18059

### 2.3 LongLLMLingua（動態壓縮）

**核心思想：** 在已取得相關段落後，依照問題相關性動態裁剪每個句子，只保留與問題直接相關的 tokens。

```
問題：「我明晚 21:30 才能到，可以入住嗎？」

LongLLMLingua 分析相關性：
  "入住截止時間為晚間 21:00" → 高相關 → 保留
  "健身房開放 06:00–22:00"   → 低相關 → 刪除
  "旅館訂房包含早餐"         → 低相關 → 刪除
```

**優點：** 針對特定問題最佳化，保留率最高。
**缺點：** 每個問題都要重新壓縮，不能預先建索引；若問題表述不清，相關性評分可能誤刪關鍵資訊。

**論文：** Jiang et al., "LongLLMLingua: Accelerating and Enhancing LLMs in Long Context Scenarios via Prompt Compression," ACL 2024. arXiv:2310.06839

## 3. 完整算例：「21:00 前入住」的例外條件

### 3.1 原始文件（政策節錄）

```
Hotel Amadeus 住宿條款（120 tokens）

[1] 標準入住時間為下午 15:00 至晚間 21:00。
[2] 旅客若預計在 21:00 後抵達，須於入住日前致電旅館確認。
[3] 旅館於確認後可安排延後入住，不另收費。
[4] 未事先確認而在 21:00 後抵達者，旅館有權取消訂房。
[5] 退房時間為上午 11:00，延遲退房須加收 50% 日費。
[6] 旅館提供行李寄存服務至晚間 22:00。
[7] 取消政策：入住日前 7 天（含）以前取消，全額退款。
[8] 入住日前 3 至 6 天取消，退款 50%。
[9] 入住日前 1 至 2 天取消，退款 20%。
[10] 當天取消或未到（no-show），不退款。
```

### 3.2 情境：旅客預計 21:30 抵達薩爾斯堡

**問題：** 「我明晚 21:30 才能到，會有什麼影響？」

**正確回答需要的句子：** [1]、[2]、[3]、[4]（共 4 句，含「21:00」這個關鍵截止時間與後續處理流程）

### 3.3 壓縮到 45 tokens 的三種結果

**方法 A：直接截斷（選前 45 tokens）**
```
標準入住時間為下午 15:00 至晚間 21:00。旅客若預計在 21:00 後抵達，須於入住日前致電旅館確認。旅館於確認後...
```
保留句：[1]、[2]、部分[3]。**遺漏** [4]（未事先確認的後果）。
例外條件保留率：3/4 = **75%**。
任務結果：LLM 知道要打電話，但不知道不打電話的後果，回答不完整。

**方法 B：抽取式摘要（選重要性最高的句子）**

若重要性評分以取消費率為主軸（這是較常被問的問題），評分可能是：
[7]、[8]、[9]、[10]（取消政策）> [1]、[2]（入住時間）> [3]、[4]（晚到確認）

選出 45 tokens 的摘要：
```
取消政策：7天前全額退款，3–6天退50%，1–2天退20%，當天不退款。
```
保留句：[7]–[10]。**完全遺漏** [1]、[2]、[3]、[4]。
例外條件保留率：0/4 = **0%**。
任務結果：LLM 完全無法回答「21:30 能入住嗎」，只能回答取消費率。任務**失敗**。

**方法 C：LongLLMLingua（依問題相關性壓縮）**

問題：「我明晚 21:30 才能到，會有什麼影響？」
相關性高的句子：[1]、[2]、[3]、[4]（入住截止與晚到處理）

壓縮後 45 tokens：
```
入住截止 21:00。21:00 後抵達須致電確認。確認後可延後入住。未確認者旅館可取消訂房。
```
保留句：[1]、[2]、[3]、[4]（關鍵語意全保留，只壓縮措辭）。
例外條件保留率：4/4 = **100%**。
任務結果：LLM 能正確回答「需要提前打電話，否則可能被取消訂房」。任務**成功**。

## 4. token 預算比較表

以同一份 Hotel Amadeus 政策（120 tokens），針對問題「21:30 能入住嗎」，三種方法在不同 token 預算下的表現：

| Token 預算 | 壓縮比 | 直接截斷保留率 | 抽取式保留率 | LongLLMLingua 保留率 |
|-----------|--------|---------------|-------------|----------------------|
| 2048      | 0%（全文）| 100%        | 100%        | 100%                 |
| 512       | 57%    | 100%（全部入住條款仍在） | 50%（入住條款被取消條款擠掉） | 100% |
| 128       | 83%    | 75%（遺漏未確認後果）   | 25%（僅剩取消費率摘要）      | 100% |
| 45        | 62.5%（相對 120）| 75% | 0%          | 100%                 |
| 20        | 83%    | 0%（句子截斷不完整）    | 0%          | 75%（壓縮措辭有資訊遺失） |

**關鍵觀察：**
1. 在中等預算（512 tokens）下，三種方法差異不大，但問題換成「取消政策」時，抽取式和 LongLLMLingua 的優劣可能互換。
2. 預算越緊（45–128 tokens），LongLLMLingua 因為「針對問題壓縮」的優勢越明顯。
3. 預算極小（20 tokens）時，所有方法都難以保留完整語意；此時應該換策略（例如只送最相關段落，而非壓縮整份文件）。

## 5. 方法比較與選型

| 面向 | 抽取式摘要 | RAPTOR | LongLLMLingua |
|------|------------|--------|---------------|
| 壓縮原理 | 選原句 | 聚類+生成摘要樹 | 依問題相關性裁剪 |
| 建索引成本 | 低 | 高（多次 LLM 呼叫） | 無（查詢時才壓縮） |
| 查詢延遲 | 低 | 低（索引已建好） | 中（即時壓縮） |
| 廣泛問題 | 差 | 佳（上層摘要） | 中（需清楚問題） |
| 細節/例外問題 | 中（選句準確性依賴評分） | 佳（下鑽原文） | 佳（針對問題） |
| 幻覺風險 | 無（原句） | 有（生成摘要可能改寫） | 低（主要裁剪不改寫） |
| 適用場景 | 靜態文件庫，問題類型多樣 | 大型文件集，需多層索引 | 已知問題，預算緊張 |

**選型建議：**
- 文件庫固定、問題類型多樣 → RAPTOR（建一次索引，查多種問題）
- 問題明確、需要最大化例外保留率 → LongLLMLingua
- 資源有限、不能呼叫 LLM 壓縮 → 抽取式（至少不引入幻覺）
- 預算充足 → 直接送全文，不壓縮

## 6. 習題

**題 1（機制）：** RAPTOR 的「遞迴聚類」如何讓同一系統同時回答廣泛問題和細節問題？以旅館政策為例，說明「今晚幾點要退房」和「旅館有什麼設施」這兩個問題會分別在哪一層索引找到答案。

<details><summary>解答</summary>

RAPTOR 的索引結構類似樹：
- **層級 0（葉節點）：** 原始段落，包含「退房時間為上午 11:00」這個精確句子。
- **層級 1（群組摘要）：** 把相關段落聚類後生成摘要，例如「入住退房規則群組」包含入住截止 21:00、退房 11:00、延遲退房加收費用等。「設施群組」包含早餐、健身房、行李寄存。
- **層級 2（全文摘要）：** 整份文件的高層摘要，例如「薩爾斯堡住宿規則與設施說明」。

**「今晚幾點要退房」（細節問題）：**
查詢嵌入會與「退房時間為上午 11:00」這句話最相似 → 優先命中層級 0 葉節點 → 答案：11:00。

**「旅館有什麼設施」（廣泛問題）：**
查詢嵌入與「設施」相關 → 命中層級 1 的「設施群組摘要」→ 答案：早餐、健身房（開放 06:00–22:00）、行李寄存（至 22:00）等。

如果廣泛問題只在層級 0 搜尋，可能需要掃描所有段落才能拼湊出完整設施列表，效率低。RAPTOR 的多層索引讓廣泛問題可以在高層摘要直接找到聚合答案。

</details>

---

**題 2（手算）：** 一份訂位確認信有 8 個關鍵事實（入住日期、退房日期、房型、早餐、21:00 截止、取消政策、旅館電話、地址）。把它壓縮到 60 tokens 後，只保留前 5 個事實，遺漏了後 3 個。計算例外條件保留率。若「21:00 截止」是唯一的例外條件（其他 7 個都是一般資訊），這個壓縮版本對「21:30 能入住嗎」這個問題的任務成功率是多少？

<details><summary>解答</summary>

**例外條件保留率計算：**
- 關鍵例外條件：「21:00 截止」（1 個）
- 壓縮後保留的事實：入住日期、退房日期、房型、早餐、21:00 截止（5 個中包含 21:00 截止）
- 例外條件保留率 = 1/1 = **100%**

雖然整體保留率是 5/8 = 62.5%，但針對「21:30 能入住嗎」這個問題，關鍵的例外條件「21:00 截止」有被保留。

**任務成功率：**
LLM 知道 21:00 是截止時間，可以判斷 21:30 超過截止。但因為遺漏了「旅館電話」（無法告知旅客應該打哪支電話確認），以及「取消政策」（無法說明不打電話的後果），回答會是**部分正確**。

若定義任務成功為「能完整回答問題，包含應採取的行動」，成功率約為 60%（知道超時，但無法給出完整行動指南）。若定義為「至少知道超時的事實」，成功率為 100%。

這個例子說明：任務成功率的定義要明確，「知道有問題」和「能完整指導行動」是不同層次的成功標準。

</details>

**題 3（選型）：** 一個旅遊助理系統需要回答各種問題（訂位查詢、政策諮詢、行程建議），文件庫有 500 份文件，每份 2000–5000 tokens。LLM 的 context window 是 4096 tokens。建議用什麼壓縮策略？說明理由並指出主要風險。

<details><summary>解答</summary>

**建議策略：RAPTOR + LongLLMLingua 二階段。**

**理由：**
1. 問題類型多樣（訂位/政策/行程）→ 無法每次都針對特定問題壓縮，需要可搜尋的索引 → RAPTOR 建多層索引適合。
2. 文件庫大（500 份）→ 一次送入全部文件不可能，需要先用索引縮小候選範圍。
3. context window 4096 tokens，單份文件可達 5000 tokens → 即使取到正確文件，也需要壓縮才能放入 → 加一層 LongLLMLingua 針對具體問題進一步壓縮候選段落。

**流程：**
1. 用 RAPTOR 對 500 份文件建多層索引。
2. 收到問題後，在索引中取得最相關的 10 個段落（約 2000 tokens）。
3. 用 LongLLMLingua 把 2000 tokens 壓縮到 1500 tokens，針對問題保留關鍵例外條件。
4. 連同問題送入 LLM（1500 + 500 tokens prompt ≈ 2000 tokens，在 4096 內）。

**主要風險：**
1. **RAPTOR 聚類錯誤：** 若例外條件（如 21:00 截止）被聚類到「不重要」的群組，查詢時可能在第 2 步就沒有取到相關段落，後續壓縮無法補救。
2. **LongLLMLingua 問題表述依賴：** 若用戶問題措辭模糊，相關性評分可能誤刪關鍵內容。
3. **建索引成本：** RAPTOR 需要對 500 份文件多次呼叫 LLM，建索引費用和時間較高，需要排程定期重建。

</details>
