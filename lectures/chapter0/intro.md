# 知識工程師的角色與協作

[總目錄](../../README.md#課程地圖) · [下一頁 →](../chapter1/intro.md)

## 本章定位

在學任何技術之前，先搞清楚你要扮演什麼角色、要交付什麼、要和誰合作。這一章不考技術，考的是「如何把技術轉成公司看得見的價值」。

---

## 什麼是知識工程師？

**知識工程師（Knowledge Engineer）** 負責把組織裡分散、隱性、不一致的知識，變成 AI 系統能正確使用的結構化資產。

這個角色站在三個世界的交叉點：

| 世界 | 他們問的問題 | 你的橋接工作 |
|---|---|---|
| **業務方**（業務、PM、法務） | 系統現在能回答什麼問題？ | 把業務規則轉成可執行的規格 |
| **工程方**（後端、ML、DevOps） | 資料格式是什麼？準確率多少？ | 設計評估方案，定義驗收標準 |
| **使用者** | 為什麼系統這樣回答？ | 設計可解釋的引用機制 |

你不是只寫程式的工程師，也不是只提需求的 PM。你是讓兩邊能對話的人。

## 一個知識工程專案的生命週期

```
需求訪談 → 知識盤點 → 資料採集 → 知識結構化
    ↓
評估設計 → 系統建構 → 驗收上線 → 持續監控與更新
```

每個階段的工作和交付物：

### 1. 需求訪談

**目標**：弄清楚系統要回答什麼問題，以及什麼答案算對。

用 **Critical Decision Method（CDM）** 訪談業務專家：
- 請描述一個你曾經處理過、比較難判斷的案件
- 當時你看到什麼線索？
- 哪個資訊讓你決定這樣處理？
- 如果那個資訊不同，你會怎麼做？

**交付物**：需求文件，包含 10-20 個代表性的「問題-正確答案-所需證據」三元組。

### 2. 知識盤點

**目標**：找出知識在哪裡、格式是什麼、誰能更新它。

常見的知識來源：

| 類型 | 例子 | 挑戰 |
|---|---|---|
| 文件型 | PDF 規章、Word SOP | 版本多、格式不一 |
| 資料庫型 | ERP、CRM 系統 | 欄位定義不清楚 |
| 人腦型 | 老員工的經驗 | 沒有文字化 |
| 流程型 | Jira 工單、email 往返 | 分散、有噪音 |

**交付物**：知識清單，每項記錄來源系統、更新頻率、負責人、格式、已知品質問題。

### 3. 資料採集與結構化

這是課程主體（Chapter 1-3）：把原始資料變成可查詢的知識。

**交付物**：結構化知識庫（決策表、知識圖譜、向量索引）+ 資料血緣文件。

### 4. 評估設計

**這步最容易被跳過，也最容易讓你被打臉。**

在系統建好之前就要設計評估方案：
- 什麼算一個正確答案？
- 誰來標注？
- 測試集怎麼切分才不洩漏？

**交付物**：評估資料集（至少 50 筆，涵蓋主要失敗模式）、評估指標定義。

### 5. 系統建構與驗收

建構（Chapter 4）→ 評估（Chapter 5）→ 迭代

**交付物**：系統、效能報告（按切片分析）、已知限制文件。

### 6. 持續監控與更新

知識會過期。規章更新、政策改變，系統就要跟著更新。

這是 Chapter 6 的內容：怎麼更新知識、怎麼驗收不破壞舊功能。

**交付物**：更新流程 SOP、回歸測試套件、版本記錄。

## 與各角色的協作方式

### 與業務方

**業務方的痛點**：他們不懂 AI，但他們是知識的來源。

實用技巧：
- 不要說「我們需要訓練資料」→ 改說「我們需要 20 個有代表性的案例，每個告訴我正確答案是什麼」
- 不要說「模型準確率 85%」→ 改說「100 個問題，系統答對 85 個，以下是它常答錯的情況」
- 把每次更新需求轉成「這會影響哪個規則、哪個測試案例」

**關鍵會議**：每兩週一次「案例審查會」，業務方看系統答錯的案例，確認是哪裡有問題。

### 與工程方

**工程方的痛點**：他們不知道知識工程師需要什麼介面。

你需要定義：
- **資料格式**：知識庫的 schema，包括哪些欄位是必填的
- **API 介面**：系統怎麼查詢知識（搜尋、精確查詢、版本查詢）
- **更新介面**：誰能改、怎麼觸發重新索引、怎麼回滾

**交付物**：知識庫 API 規格文件（輸入輸出格式、版本控制行為）。

### 與 ML 工程師

ML 工程師負責模型，你負責資料和知識。邊界在哪裡？

| 你負責 | ML 工程師負責 |
|---|---|
| 標注資料的品質與覆蓋率 | 模型架構選型 |
| 評估資料集設計（不洩漏） | 訓練與超參數 |
| 決定「答對」的定義 | 模型評估指標的實作 |
| 知識更新後的回歸測試 | 模型版本管理 |

## 向管理層報告的方式

管理層不看 F1 score，他們看：

1. **這個系統幫我省了什麼？**
   - 每週節省多少人工審核時數？
   - 轉人工的比例從多少降到多少？

2. **系統還有哪些做不到？**
   - 明確說明已知限制，建立信任
   - 「這種類型的問題目前準確率只有 70%，原因是……，計畫在 Q2 改善」

3. **出問題時怎麼辦？**
   - 有沒有回滾機制？
   - 有沒有轉人工的 fallback？

**報告模板**：
```
本月處理 N 筆案件
- 自動處理：X 筆（占 X%），準確率 X%
- 轉人工：Y 筆（占 Y%）
- 本月新增案例覆蓋：Z 個新情境
- 下月計畫：改善 [具體切片] 的準確率，預計從 X% 升到 Y%
```

## 常見陷阱

### 陷阱一：先建系統再想評估

問題：等建好才發現不知道什麼算對，沒辦法量化改進。

解法：**先設計 20 筆評估案例，再開始建系統。** 這 20 筆就是你的驗收標準。

### 陷阱二：知識更新沒有版本控制

問題：政策改了，直接覆蓋，出問題不知道是什麼時候改壞的。

解法：每次更新都留版本，每筆決策記錄「用了哪個版本的知識」。

### 陷阱三：只量整體準確率

問題：整體 90%，但「跨日夜車」這種邊緣情況全錯，業務方卻天天碰。

解法：**按切片報告**（邊緣情況、版本衝突、缺資料分別算）。

### 陷阱四：知識工程師兼任標注員

問題：你設計了系統，又自己標注，你的偏見會進入訓練資料。

解法：設計者和標注員分離。你設計標注指南，請業務方標注。

## 習題

1. **角色設計**：你剛加入一家保險公司，要建立一個「理賠助理」知識系統。請列出你在第一個月內需要訪談的三種角色，以及對每種角色要問的兩個關鍵問題。

<details>
<summary>參考答案</summary>

**理賠業務員**（知識來源）
- 你最常遇到的「難判斷」案件是哪種？
- 有沒有哪個條文你自己都要查一下才確定？

**IT 系統負責人**（資料來源）
- 理賠相關的資料存在哪些系統？格式是什麼？
- 更新頻率如何？有沒有 API？

**合規/法務**（知識更新觸發者）
- 條款更新的頻率和流程是什麼？
- 新版本上線前需要哪些審核步驟？

</details>

2. **交付物設計**：你的主管問你「知識系統準備好了嗎？」。請設計一份一頁的驗收報告，列出你認為應該包含的五個項目，並說明每項為什麼重要。

<details>
<summary>參考答案</summary>

1. **評估資料集結果**（N 筆，整體準確率 X%）：讓主管知道有客觀標準，不是感覺好就上線
2. **切片分析**（主要失敗模式各切片的準確率）：避免整體高但邊緣情況全錯
3. **已知限制**（系統目前不能處理哪種問題）：建立信任，避免上線後被打臉
4. **轉人工比例與流程**（有多少會轉人工，誰來處理）：確認有 fallback
5. **版本與回滾機制**（出問題能在多久內回滾）：讓主管安心

</details>

3. **陷阱識別**：你的同事說「我們先把所有文件都丟進去，建好 RAG 系統，再來看效果怎樣」。請指出這個做法的兩個風險，並說明如何改進。

<details>
<summary>參考答案</summary>

**風險一：沒有評估標準**
先建系統再來「看效果」，沒有人知道什麼叫做「夠好」。可能花三個月調參數，卻沒有進步的量化依據。
改進：先設計 30 筆評估案例，定義指標，再開始建系統。

**風險二：垃圾進垃圾出**
「所有文件都丟進去」包含了過期版本、錯誤的文件、格式混亂的掃描檔。
改進：先做知識盤點，決定哪些文件要進去、哪些要清洗、哪些要排除，再建索引。

</details>
